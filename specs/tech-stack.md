The SDK calls of the three adapters were checked against the installed packages. The OpenRouter path works; the OpenAI path is implemented from documentation and unverified (see Key conventions).

The application is a desktop, interactive application used by one person: it is not a service in a container and not a batch runner.

The design uses internal neutral types (Message, ToolCall, Usage, stream events) and three thin adapters, one per SDK. It does not use a gateway library such as LiteLLM, because own adapters keep full control over messages, context and tool calls (assumption; the choice of own neutral types and three adapters stands). It does not use the OpenAI Responses API as the canonical shape.

Model registry, in `~/.config/llm-harness/models.yaml` (YAML, separate from the TOML connection settings, and holding no keys): a list under `models:` where each entry has `id` (stable identifier used on the command line and in the UI), `name` (display name), `provider` (the id of a provider declared in `config.toml`), `model` (the provider's own model id), `tags`, `priority` and `price` (`input_per_mtok` and `output_per_mtok`; an omitted price means 0, which suits local models) and an optional `thinking` (`true` or `false`; omitted means the model's own default). The command-line flags `--think` and `--no-think` override `thinking` for one run; precedence: flag, then model `thinking`, then the model's default. These key names are confirmed by the author. The orchestrator model is the model tagged `orchestrator` with the highest priority (`select_orchestrator_model`; a higher number wins, a tie at the top is an error, no model with the tag stops startup with a message naming the tag, and there is no fallback to `default` for this role); `--model <id>` or a UI selector overrides it. The tag `embedding` marks embedding models (built, see the Embeddings bullet); a model with it cannot carry `chat`, `default` or `orchestrator` (rejected at config load), it is hidden from the UI model selectors (`chat_models`), and `--model` rejects it. The harness picks a model for a task by matching tags, then by priority. A subagent declares required tags (its agent's `model_tags`), and among the configured models carrying all of them the highest priority wins (`select_agent_model`). The file is loaded and validated, the orchestrator model is chosen by tag and priority, and the models appear in the UI selectors. Fallback chain (`model-registry`): the chosen model first (the user's pick, or the orchestrator model), then the other models carrying the required tags by priority (highest first, ties in file order), then the models tagged `default` by priority, duplicates removed; the pure rule is `fallback_chain` in `routing.py`, which takes the required tags as a parameter; every front end passes `orchestrator` (`make_router_factory(..., required_tags=frozenset({"orchestrator"}))`); the router's own default is still `chat`. Triggers: a terminal error of kind `connection`, `rate_limit`, `not_found`, `unknown` or `auth` before any output moves to the next model; `bad_request` is shown directly, a failure after output started is shown as an error, and a cancellation is never a failure. A failing model goes into backoff, persisted in SQLite: 1, 2, 3, 5, 10, 15, 30 and 60 minutes for consecutive failures (capped at 60), reset on success; automatic choices skip a model in backoff, while a manual pick (`--model` or a UI selector change) is tried anyway. When every model failed or is in backoff, the turn ends with `no model available: ...; pick a model to try it now`. Usage ledger: every attempt, failed ones too, is one row in the SQLite table `llm_calls`; cost is (input tokens x `input_per_mtok` + output tokens x `output_per_mtok`) / 1,000,000, an omitted price is 0, and unknown usage is stored as NULL and shown as `?`. After each successful turn every front end shows a usage line, `[<model> tokens in=<n> out=<n> reasoning=<n> $<cost> <s>s | session $<total>]`, and a note line when a fallback happened. When `models.yaml` does not exist, the app stops with a message that names the path and offers to write an example file; there is no hidden built-in default model.

Orchestrator and context: the orchestrator sends the model only its instructions, a typed state and the latest observation, never the history; state changes only through validated patches; and one place builds every model request. The orchestrator context is typed state holding the goal, the collected information each with its source, and the plan, plus the latest observation. The orchestrator tracks the user's current goal at all times; the goal may change, and if the orchestrator has no clue what the goal is, it asks the user questions. The context always includes the current date and time, the user's name and the computer name. For external memory the orchestrator must recognise that, on another computer, it is talking to the same user under a different name, so it can reach memories about that user. How this identity is established is an open design question for a feature spec. A single context-builder component is the only place that builds a model request. The model replies with one JSON object with exactly two keys, `state_patch` and `action`. `state_patch` may contain only `goal`, `findings` and `plan`; `null` deletes a value; lists change only through `{"$append": [...]}` or `{"$replace": [...]}`; `environment`, `goal_history`, `turn` and `step` are protected; the serialized state is capped at 8000 characters; `goal_history` keeps the newest 20 records; a finding needs a non-empty `source`. `action` is a tagged union on `type`: `respond`, `ask_user`, `call_tool`, `delegate`. A rejected reply changes nothing and its error text becomes the next observation; at most 2 retries per step and 8 steps per turn. One code fence around the whole reply is tolerated. State and reply types are in `state.py`; `context.py` holds `build_request`, the only builder of the orchestrator's `ChatRequest`; `orchestrator.py` holds `Orchestrator` (`send`, `snapshot`, `restore`). `ToolRegistry` (`tools.py`) does name lookup only; typed input and output schemas are deferred to `tools-first-set`. An unknown or failing tool becomes an observation. `ChatRequest.response_schema` (optional JSON schema) is sent by the Ollama adapter as the `format` argument; the OpenAI-compatible and Vertex adapters ignore it.

Context inspector: the UI shows streaming thinking traces (reasoning text from models that provide it) and lets the user inspect, at any moment, the orchestrator's current context: goal, collected information with sources, plan, and what will be sent to the model next. Because the single context-builder builds every model request, the inspector shows exactly what is sent (design intent, assumption). Thinking traces are display-only and are never written back into the orchestrator state.

Subagents (built, `subagents`): a subagent is an agent in `agents.yaml` without the tag `orchestrator` and with non-empty `examples` (`delegation_targets` in `context.py`); every request lists them under `## Subagents` as `id: description (e.g. examples)`. The orchestrator's `delegate` action (`subagent`, `brief`) runs the child as a second `Orchestrator` with its own typed state (goal preset from the brief), the parent's environment block and only `tools_for(child)` (`subagents.py`, `Orchestrator._delegate`). Decisions (human, 2026-10-29): depth 1 only (a child `delegate` is answered with `delegate is not available to subagents`); at most 5 steps (`SUBAGENT_MAX_STEPS`) and 2 retries per reply; the child receives only the brief, never the history or the parent's state; a child `respond` returns its text plus findings as `- text (source: s)` lines, a child `ask_user` ends the delegation and returns `needs: <question>` (the user is not asked directly); a step limit, an error or a failure to start become observations, never a parent error; an unknown or ineligible id gives `unknown subagent <id>; available subagents: a, b`; the child's thinking, notices, model switches and usage are forwarded to the user, its text and Done are not. The child's model is `select_agent_model(config, agent)` (top priority among non-embedding models carrying all the agent's `model_tags`; a tie raises) behind a fresh router per call. Session cost (human, 2026-10-29): a child router feeds the parent router's `SessionCost`, so the shown total never decreases; the total resets per session (each new chat, model change or GUI client starts at $0). Trace: a `subagent` span holds the child's spans and its final `state` (in `LONG_FIELDS`). Not built: grant/revoke, nesting beyond depth 1, parallel delegation, persisting child state across turns, a ledger `agent_id` column, per-agent cost reports, and a State-tab section for the child.

Agent registry (built): `~/.config/llm-harness/agents.yaml`, next to `models.yaml`, a list under `agents:` where each entry has `id`, `name`, `description`, `tags`, `model_tags` and optional `examples`, `tools` and `deny` (`AgentConfig` in `config.py`). `tags` and `model_tags` are lowercase with no spaces or repeats. Ids are unique, and a name in both `tools` and `deny` is rejected. Every agent's `model_tags` must be carried together by one chat model. Exactly one agent carries the tag `orchestrator`. A missing file stops the app and offers an example, like `models.yaml`. Decision (human, 2026-10-29): the orchestrator takes its id and tags from the agent (`find_orchestrator_agent`), while its model is still chosen by the model tag; `tools` and `deny` are used by `tools_for` (`tool-registry`), `examples` decide which agents are subagents, and `model_tags` choose a subagent's model (`subagents`).

Tools (planned, the author will write them): web search, RAG query, memory access, and pre-programmed web scrapers or API calls. Each tool has a typed input (a pydantic model); its result is a string. Local Ollama has the embedding models bge-m3 and nomic-embed-text (both present, checked 2026-10-28); bge-m3 is the chosen first embedding model (see the Embeddings bullet) and nomic-embed-text a possible alternative. Tools and agents carry tags; an agent is given the tools whose tags intersect its own, matched automatically with no model call. The orchestrator additionally gets a `tool_search` tool and can grant or revoke tool names for one delegation, only within an allowlist in config. The registry idea follows an existing course notebook (index each tool's name and description, return the top K matches) with the vector store as the index; a registry is worth its cost at roughly 10 or more tools or 10k or more tokens of definitions (the notebook's own heuristic). Built (`tool-registry`, decided by the author 2026-10-29): `Tool` (`name`, one-line `description`, `tags`, `input_model`, `run`) and `ToolRegistry` in `tools.py`; `tools_for(agent)` (tags intersect, plus `tools`, minus `deny`, no model call); lexical `search` (a query word scores 3 in the name, 2 in a tag, 1 in the description, at the highest place found); `tool_search` and `build_tool_registry` in `builtin_tools.py`; a `## Tools` section (name and description only) in every request; `call_tool` outside the agent's set or with invalid arguments is refused as an observation; unknown tool names in `agents.yaml` stop startup; the State tab shows the tools and an estimate (4 characters per token) of the listing against the full schemas. Not built: grant/revoke on `delegate` with the `[tools] grantable` allowlist (it was left out of `subagents`; still open), vector fusion in `search`, typed output, and any real tool (`tools-first-set`).

## Key conventions

- Naming: snake_case for Python and TOML keys, UPPER_SNAKE for environment variables. Config key names are confirmed (see the decision on connection settings below); agent keys are confirmed (see Agent registry); tool identifiers are confirmed (lowercase letters, digits and underscores, starting with a letter); subagent identifiers are agent ids from `agents.yaml` (confirmed, see Agent registry).
- All Python work goes through uv: add dependencies with `uv add`, run everything with `uv run`; never `pip install` and never edit `uv.lock` by hand.
- Command line: `llm-harness` starts the terminal UI, which needs a terminal for input and output; without one it prints a hint to use `--plain` and exits with code 2. `llm-harness --gui` starts the web GUI on 127.0.0.1 port 8080 and opens the user's browser; there is no port flag. `llm-harness --plain` is a permanent line-based chat mode that works over pipes and in tests; `/exit`, `/quit` or end of input ends it, and Ctrl-C exits with code 130. `--plain` and `--gui` are mutually exclusive. Typed as the whole chat input (stripped, case-insensitive), `/quit` ends the application in every front end (`/exit` too in `--plain` and the terminal UI; the terminal UI also quits with Ctrl+Q); it is not sent to the model, and a message that merely contains it is an ordinary message. Ctrl-C in `--gui` shuts the server down cleanly and exits with code 130, with no traceback; the terminal UI does not react to Ctrl-C (Textual's design). `--model <id>` selects a model by its `models.yaml` id. `--think` / `--no-think` (mutually exclusive) override the model's `thinking` setting for one run.
- UIs contain no provider-specific code.
- GUI and widget layout: use the full browser width and the full viewport height; the message area grows with the window; base text is at least 18px and secondary text at least 15px; no narrow centred columns, no fixed-height boxes, no tiny text. This applies to every GUI page and to the planned A2UI widgets.
- Adapters are the only place that import a provider SDK.
- asyncio streaming throughout.
- Tests are offline by default.
- Configuration lives in files in the home directory, not in the repository. An API key is given either inline in the config or as a reference to an environment variable to read it from; no other mechanism is supported.
- Decision: connection settings are TOML, read with stdlib `tomllib`, at `~/.config/llm-harness/config.toml`. Each `[providers.<id>]` entry has `type` (ollama | openai | vertex), `base_url`, `api_key` or `api_key_env` (an inline key or an environment variable name, not both) and, for Vertex, `project` and `location`. An optional `reasoning_style` (`"openai"`, the default, or `"openrouter"`) is valid only on `type = "openai"` providers; on an ollama or vertex provider it is a config error. It selects how the OpenAI-compatible adapter sends the model's `thinking` toggle: style `openai` sends `reasoning_effort="none"` for `false` and `reasoning_effort="medium"` for `true`; style `openrouter` sends `reasoning: {"enabled": false}` or `reasoning: {"enabled": true}` through the SDK's extra request body; with no `thinking` value nothing is sent. Models are declared in `models.yaml` (see the model registry above). These key names are confirmed by the author. Validation rules: `base_url` must be an http(s) URL with a host and no credentials; an `ollama` provider requires `base_url` and accepts no key; an `openai` provider requires `base_url` and exactly one key source; a `vertex` provider requires `project` and `location` and accepts no `base_url` and no key; unknown keys are rejected in both files (`models.yaml` may contain only `models`); `priority` and `price` values must be finite numbers; two `default` models with the same top priority are an error.
- Built: a top-level `user_id` key in `config.toml` (optional, a stable string, the same on every computer, at most 128 printable characters, kept as written). Built: the optional `[storage]` table with `[storage.relational]` (`backend`, `path`), `[storage.vector]` (`backend`, `path`) and `[storage.files]` (`backend`, `root`); paths are absolute or start with `~`; `postgres` and `qdrant` are recognised and rejected with a message naming `storage-backends-remote`. There is no `[embeddings]` table: embedding models are `models.yaml` entries tagged `embedding`, with a built optional `dimensions` field on an entry (passed to the provider only when set) and a built rule that rejects an entry tagged `embedding` together with `chat`, `default` or `orchestrator`. The example `models.yaml` the program offers to write includes a commented-out embedding entry. Secrets keep the existing `api_key_env` pattern, and a Postgres DSN would be a `Secret` that prints as `[REDACTED:...]`.
- Warn on stderr, naming the path and the fix, when `config.toml` is readable or writable by group or other (`chmod 600`) or when the config directory is writable by group or other (`chmod 700`). Example files are created with mode 0600 (`config.toml`) and 0644 (`models.yaml`), in a directory with mode 0700.
- Never print or log keys. A `Secret` prints as `[REDACTED:api_key]`, and every provider error message goes through `redact()`, which masks configured keys, `Authorization`, `x-api-key` and `api-key` values, URL credentials, bearer tokens, `sk-` keys, Google `AIza` keys and JWT-shaped strings before it truncates the message to 300 characters.
- Model output is untrusted: every front end passes it through `sanitize_text` (in `display.py`). Assistant replies are then rendered as markdown by `markdown_render.py`; everything else (thinking text, usage line, error lines, notes, the echoed user text) stays plain text (`ui.label` and `Static(markup=False)`), and `--plain` stays plain text. Raw HTML in the source is never interpreted (`html=False`): it shows as literal text. Images are never rendered or loaded: an image becomes its escaped alt text, because an injected image URL could leak the conversation. Links: `href` only `http`, `https`, `mailto` or a `#fragment`; external links get `rel="noopener noreferrer"` and `target="_blank"`, fragment links get `rel` but no `target`. In the web UI the pipeline is `sanitize_text`, `render_html`, `sanitize_html` (nh3 allowlist, run twice) and `ui.html(content, sanitize=sanitize_html)`: NiceGUI applies a callable `sanitize` on the server and only `sanitize=True` triggers the browser's DOMPurify, so our allowlist is the only filter; never use `ui.markdown`, and never pass `sanitize=True` or `sanitize=False`. The allowlist has no `script`, `style`, `iframe`, `object`, `embed`, `form`, `svg`, `img` or `style` attribute; `class` and `id` values are restricted. In the terminal UI, replies use Textual's `Markdown` widget with `parser_factory` and `open_links=False`. `sanitize_text` removes ESC, control characters other than newline and tab, DEL, C1 controls, bidi controls and the line and paragraph separators U+2028 and U+2029.
- Markdown extensions live in one place, the `_EXTENSIONS` tuple in `src/llm_harness/markdown_render.py` (CommonMark plus tables, strikethrough, linkify, task lists and footnotes); adding one is a one-line change. The terminal UI's Textual `Markdown` widget cannot show task lists (the checkbox is raw inline HTML that Textual drops) or footnotes (Textual raises `IndexError` on footnote tokens), so those two plugins are left out of its parser (`_TEXTUAL_UNSUPPORTED`) and their syntax shows as literal text there. Table column alignment is dropped in the web UI because `style` attributes are not allowed.
- The web GUI has no login. It binds 127.0.0.1 only, rejects any request whose Host or Origin is not `127.0.0.1:<port>` or `localhost:<port>` with HTTP 403, and keeps one chat session per browser client. Never bind another address.
- Front ends show an unexpected exception as the single line `error (unexpected): <Type>: <redacted message>`, never a traceback or local variables; the plain mode prints provider errors as `error (<kind>): <message>`.
- Thinking traces are display-only and never written back into the orchestrator state.
- Persistence: one SQLite file, by default `~/.local/share/llm-harness/harness.db` (path settable with `[storage.relational] path`), with tables `llm_calls`, `model_backoff` and `schema_versions`. It is reached through `SqliteRelationalStore` (`src/llm_harness/storage/relational.py`); `store.py` runs the ledger on it as namespace `ledger`, and versions are kept per namespace in `schema_versions`; `PRAGMA user_version` is only read to adopt an old file (`user_version` 1) and is no longer written. A file that cannot be used or has a newer version still disables the store for the process with one notice and is never deleted or migrated down. The directory is created with mode 0700 and the file with mode 0600. Only ids, token counts, costs, times and error kinds are stored, never prompts, replies, error messages or keys. All SQL is parameterized (the one `PRAGMA user_version = N` statement uses an integer the code controls).
- Storage interfaces (built, local backends only): `RelationalStore` (SQLite), `VectorStore` (`qdrant-edge`, or `none`) and `FileStore` (`local`), in `src/llm_harness/storage/`, bundled by `Storage` and built by `open_storage`. Still planned: Postgres and remote qdrant (`storage-backends-remote`); shared filesystem, garage and cloud object storage stay UNDECIDED candidates. Tools and agents read and write data only through these interfaces.
- Storage conventions: schema versions are kept per namespace in `schema_versions(namespace, version)`; the ledger's expected version is `store.expected_schema_versions()`; ledger tables keep their unprefixed names (`llm_calls`, `model_backoff`). `ToolContext(storage, user_id, agent_id, tags)` is passed to `Tool.run(arguments, ctx)`. `open_storage` creates nothing and never opens the vector shard; the `Storage` is closed on exit in plain, TUI and GUI modes. A vector collection is held open by one process and a second one gets `VectorStoreLockedError`. The ledger path rule lives in `_relational_path` in `cli.py`.
- `data_dir` is a keyword of `cli.main` for tests, not a config key; no config key was added for the fallback or the ledger. `tests/conftest.py` has an autouse fixture that sends `store.default_db_path` to a temporary path, so no test touches the real data directory; production code must call it as `store.default_db_path()` through the module for the patch to apply.
- The OpenAI-compatible adapter is verified live against Ollama's `/v1` endpoint; OpenRouter works; OpenAI is implemented from documentation and unverified.
- Every adapter hides the SDK's ambient environment variables while it builds its client (shared helper in `providers/environment.py`): `OPENAI_*` for the OpenAI-compatible adapter, `OLLAMA_API_KEY` and `OLLAMA_HOST` for Ollama, and the `GOOGLE_*` and `GEMINI_*` variables the Google SDK reads for Vertex. `base_url`, `api_key`, `project` and `location` always come from the config.
- Test-only environment variables: `LLM_HARNESS_LIVE_MODEL` (live OpenAI-compatible test) and `LLM_HARNESS_LIVE_VERTEX_MODEL` (live Vertex test). The application never reads them.
- Environment target, Ollama: local Ollama at `http://localhost:11434` is the default dev and test target. The network Ollama host is recorded in the user's home config, not in this repo.
- Environment target, GCP: the dev project and location are recorded in the user's home config, not in this repo. Always pass them explicitly from config, never from ambient environment defaults (no reliance on `GOOGLE_CLOUD_PROJECT` or the gcloud default). Vertex auth uses Application Default Credentials.
- Environment target, database: `~/.local/share/llm-harness/harness.db` is the real ledger; tests and live runs must use a temporary directory (the autouse fixture, or `data_dir`).
- Environment target, OpenAI and OpenRouter: calls are metered and shared; use only small prompts in tests and smoke runs.
- No production target exists.
