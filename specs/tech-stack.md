# Tech stack

## Languages & runtimes

- Python >= 3.12, managed by uv (the interpreter is selected through `.python-version`). The 3.12 floor is an assumption.
- Library versions were checked on PyPI on 2026-10-27 as the latest releases; a uv lockfile pins the exact versions.
- Planned, not yet used (roadmap item `a2ui-nicegui`): TypeScript for the web UI widgets, compiled with esbuild. No TypeScript, JavaScript, CSS or `package.json` file exists in the repository yet. Latest npm releases checked on 2026-10-27: esbuild 0.28.2, typescript 7.0.2, lit 3.3.3. Node v26.8.2 is present on the dev machine. Once the frontend exists, Node, npm, esbuild and TypeScript will be needed only on the developer and release machine; end users install the Python package without Node.js.

The SDK calls of the three adapters were checked against the installed packages. The OpenRouter and OpenAI paths are implemented from documentation and are untested (see Key conventions).

The application is a desktop, interactive application used by one person: it is not a service in a container and not a batch runner.

The design uses internal neutral types (Message, ToolCall, Usage, stream events) and three thin adapters, one per SDK. It does not use a gateway library such as LiteLLM, because own adapters keep full control over messages, context and tool calls (assumption; the choice of own neutral types and three adapters stands). It does not use the OpenAI Responses API as the canonical shape.

Model registry, in `~/.config/llm-harness/models.yaml` (YAML, separate from the TOML connection settings, and holding no keys): a list under `models:` where each entry has `id` (stable identifier used on the command line and in the UI), `name` (display name), `provider` (the id of a provider declared in `config.toml`), `model` (the provider's own model id), `tags`, `priority` and `price` (`input_per_mtok` and `output_per_mtok`; an omitted price means 0, which suits local models) and an optional `thinking` (`true` or `false`; omitted means the model's own default). The command-line flags `--think` and `--no-think` override `thinking` for one run; precedence: flag, then model `thinking`, then the model's default. These key names are confirmed by the author. The default model is the model tagged `default` with the highest priority (a higher number wins); `--model <id>` or a UI selector overrides it. The harness picks a model for a task by matching tags, then by priority. Assumption: a task or subagent declares required tags, and among the configured models carrying all of them the highest priority wins. The file is loaded and validated, the default is chosen by tag and priority, and the models appear in the UI selectors. Fallback chain (`model-registry`): the chosen model first (the user's pick, or the default), then the other models tagged `chat` by priority (highest first, ties in file order), then the models tagged `default` by priority, duplicates removed; the pure rule is `fallback_chain` in `routing.py`, which takes the required tags as a parameter (chat turns pass `chat`). Triggers: a terminal error of kind `connection`, `rate_limit`, `not_found`, `unknown` or `auth` before any output moves to the next model; `bad_request` is shown directly, a failure after output started is shown as an error, and a cancellation is never a failure. A failing model goes into backoff, persisted in SQLite: 1, 2, 3, 5, 10, 15, 30 and 60 minutes for consecutive failures (capped at 60), reset on success; automatic choices skip a model in backoff, while a manual pick (`--model` or a UI selector change) is tried anyway. When every model failed or is in backoff, the turn ends with `no model available: ...; pick a model to try it now`. Usage ledger: every attempt, failed ones too, is one row in the SQLite table `llm_calls`; cost is (input tokens x `input_per_mtok` + output tokens x `output_per_mtok`) / 1,000,000, an omitted price is 0, and unknown usage is stored as NULL and shown as `?`. After each successful turn every front end shows a usage line, `[<model> tokens in=<n> out=<n> reasoning=<n> $<cost> <s>s | session $<total>]`, and a note line when a fallback happened. When `models.yaml` does not exist, the app stops with a message that names the path and offers to write an example file; there is no hidden built-in default model.

Orchestrator and context: the orchestrator sends the model only its instructions, a typed state and the latest observation, never the history; state changes only through validated patches; and one place builds every model request. The orchestrator context is typed state holding the goal, the collected information each with its source, and the plan, plus the latest observation. The orchestrator tracks the user's current goal at all times; the goal may change, and if the orchestrator has no clue what the goal is, it asks the user questions. The context always includes the current date and time, the user's name and the computer name. For external memory the orchestrator must recognise that, on another computer, it is talking to the same user under a different name, so it can reach memories about that user. How this identity is established is an open design question for a feature spec. A single context-builder component is the only place that builds a model request. The exact reply and state-patch contract between the model and the orchestrator is decided in the feature spec.

Context inspector: the UI shows streaming thinking traces (reasoning text from models that provide it) and lets the user inspect, at any moment, the orchestrator's current context: goal, collected information with sources, plan, and what will be sent to the model next. Because the single context-builder builds every model request, the inspector shows exactly what is sent (design intent, assumption). Thinking traces are display-only and are never written back into the orchestrator state.

Subagents: each subagent is declared in configuration with the list of tools it may use and its model tags. Only those tool definitions enter its context. It receives a fresh small brief and returns a short summary with sources into the orchestrator state.

Tools (planned, the author will write them): web search, RAG query, memory access, and pre-programmed web scrapers or API calls. Each tool has typed input and output. Local Ollama has the embedding models nomic-embed-text and bge-m3 (checked) that a RAG tool could use; this is planned only, not decided.

Web UI and A2UI: A2UI is the open declarative agent-to-UI protocol: the agent sends declarative component descriptions, and the client renders only components from its approved catalog. Decision: implement A2UI protocol v1.0 (not started; roadmap item `a2ui-nicegui`). The specification is in the A2UI repository (`https://github.com/a2ui-project/a2ui`, spec documents under `specification/v1_0/`, checked at commit 059b8d34); its basic catalog has 18 components and 14 functions (checked). a2ui.org labels v0.9.1 "Current production release" and v1.0 "Release candidate" (checked 2026-10-27); the author chose v1.0 knowingly.
- Widgets are ported to NiceGUI: the web UI renders A2UI surfaces with NiceGUI-hosted widgets, including the author's own custom components (HTML and SVG) defined in a custom catalog (custom catalogs are part of the spec).
- Frontend code is written in TypeScript and compiled with esbuild. Compiled JS and CSS bundles ship inside the Python package (wheel). Whether built bundles are committed or built at release time is to be decided in the feature spec.
- Python side, candidate only (not a decided dependency, not in the pinned list above): the PyPI package `a2ui-core` (0.4.0 on PyPI, requires Python >= 3.10, depends on babel, jsonschema, pydantic, referencing and regex). Its source in the A2UI repository contains a v1.0 schema module and a v1.0 protocol adapter (checked by grep). It provides message processing, surface and data-model state, data binding, catalog registry and validation. UNVERIFIED: that PyPI 0.4.0 matches the repository source, that it passes the v1.0 conformance cases, and how it integrates with NiceGUI.
- UNVERIFIED, needs a bounded spike before a feature spec: where in the A2UI repository the Lit widget implementations live and how much of them is portable; how a NiceGUI page hosts compiled TypeScript widgets (the NiceGUI custom element and static file mechanisms have not been checked against the installed version).
- The core emits typed events (for example status, message text deltas, ui). Assumption: the TUI renders text only and ignores or degrades ui events.

## Infrastructure & tooling

- Project management: uv 0.12.13 (installed on the dev machine, checked) is the only project manager. It manages the interpreter (`.python-version`, `uv python pin`), dependencies (`uv add`, `pyproject.toml`), the lockfile (`uv.lock`), the environment (`uv sync`), running (`uv run`), the wheel (`uv build`) and the global command (`uv tool install --editable .`). No pip, poetry, pip-tools, `requirements.txt` or hand-made virtualenv. The wheel will contain prebuilt frontend bundles once the frontend exists (planned); today it contains only Python modules.
- Development install (requirement): the author runs the app from a git clone, and every change in the code must apply after the clone is updated (`git pull`) and the app is restarted, with no reinstall. The install is therefore editable: `uv sync` then `uv run <command>` (the project is installed editable by default), or `uv tool install --editable .` for a global command (both flags exist in uv 0.12.13: checked). Open, to be decided in the feature spec: how the compiled frontend bundles stay current after a pull (committed to git, or built when the app starts in development), so that no manual build step is needed.
- Frontend build (planned): esbuild and TypeScript via npm, run on the developer or release machine only.
- Lint and format: ruff.
- Tests: pytest against a scripted fake provider by default. Live-LLM tests carry the pytest marker `live` and are deselected by default (`addopts` is `-m "not live"`); run them with `uv run pytest -m live`, with a small token and time budget, local Ollama first. The default pytest configuration also loads the NiceGUI test plugin (`-p nicegui.testing.user_plugin`), which a plain `uv sync` provides because nicegui is a runtime dependency.
- No CI yet. The directory is not yet a git repository.
- Layout: `src/llm_harness/` (src layout): core in `types.py`, `session.py`, `config.py`, `redact.py`, `display.py`, `markdown_render.py`, `routing.py` (pure chain, backoff and cost rules), `store.py` (SQLite ledger and backoff state), `router.py` (`ModelRouter`, which implements the provider interface and applies the chain) and `cli.py`; `providers/` (`base.py`, `environment.py` and one adapter module per SDK); `tui/` and `gui/` as separate front-end packages (each with `app.py`; `gui/` also has `security.py`); tests under `tests/`, with the scripted fake provider in `tests/fakes.py`.

## Key conventions

- Naming: snake_case for Python and TOML keys, UPPER_SNAKE for environment variables. Config key names are confirmed (see the decision on connection settings below); tool and subagent identifiers will be confirmed with the author before their features.
- All Python work goes through uv: add dependencies with `uv add`, run everything with `uv run`; never `pip install` and never edit `uv.lock` by hand.
- Command line: `llm-harness` starts the terminal UI, which needs a terminal for input and output; without one it prints a hint to use `--plain` and exits with code 2. `llm-harness --gui` starts the web GUI on 127.0.0.1 port 8080 and opens the user's browser; there is no port flag. `llm-harness --plain` is a permanent line-based chat mode that works over pipes and in tests; `/exit`, `/quit` or end of input ends it, and Ctrl-C exits with code 130. `--plain` and `--gui` are mutually exclusive. Typed as the whole chat input (stripped, case-insensitive), `/quit` ends the application in every front end (`/exit` too in `--plain` and the terminal UI; the terminal UI also quits with Ctrl+Q); it is not sent to the model, and a message that merely contains it is an ordinary message. Ctrl-C in `--gui` shuts the server down cleanly and exits with code 130, with no traceback; the terminal UI does not react to Ctrl-C (Textual's design). `--model <id>` selects a model by its `models.yaml` id. `--think` / `--no-think` (mutually exclusive) override the model's `thinking` setting for one run.
- UIs contain no provider-specific code.
- GUI and widget layout: use the full browser width and the full viewport height; the message area grows with the window; base text is at least 18px and secondary text at least 15px; no narrow centred columns, no fixed-height boxes, no tiny text. This applies to every GUI page and to the planned A2UI widgets.
- Adapters are the only place that import a provider SDK.
- asyncio streaming throughout.
- Tests are offline by default.
- Configuration lives in files in the home directory, not in the repository. An API key is given either inline in the config or as a reference to an environment variable to read it from; no other mechanism is supported.
- Decision: connection settings are TOML, read with stdlib `tomllib`, at `~/.config/llm-harness/config.toml`. Each `[providers.<id>]` entry has `type` (ollama | openai | vertex), `base_url`, `api_key` or `api_key_env` (an inline key or an environment variable name, not both) and, for Vertex, `project` and `location`. An optional `reasoning_style` (`"openai"`, the default, or `"openrouter"`) is valid only on `type = "openai"` providers; on an ollama or vertex provider it is a config error. It selects how the OpenAI-compatible adapter sends the model's `thinking` toggle: style `openai` sends `reasoning_effort="none"` for `false` and `reasoning_effort="medium"` for `true`; style `openrouter` sends `reasoning: {"enabled": false}` or `reasoning: {"enabled": true}` through the SDK's extra request body; with no `thinking` value nothing is sent. Models are declared in `models.yaml` (see the model registry above). These key names are confirmed by the author. Validation rules: `base_url` must be an http(s) URL with a host and no credentials; an `ollama` provider requires `base_url` and accepts no key; an `openai` provider requires `base_url` and exactly one key source; a `vertex` provider requires `project` and `location` and accepts no `base_url` and no key; unknown keys are rejected in both files (`models.yaml` may contain only `models`); `priority` and `price` values must be finite numbers; two `default` models with the same top priority are an error.
- Warn on stderr, naming the path and the fix, when `config.toml` is readable or writable by group or other (`chmod 600`) or when the config directory is writable by group or other (`chmod 700`). Example files are created with mode 0600 (`config.toml`) and 0644 (`models.yaml`), in a directory with mode 0700.
- Never print or log keys. A `Secret` prints as `[REDACTED:api_key]`, and every provider error message goes through `redact()`, which masks configured keys, `Authorization`, `x-api-key` and `api-key` values, URL credentials, bearer tokens, `sk-` keys, Google `AIza` keys and JWT-shaped strings before it truncates the message to 300 characters.
- Model output is untrusted: every front end passes it through `sanitize_text` (in `display.py`). Assistant replies are then rendered as markdown by `markdown_render.py`; everything else (thinking text, usage line, error lines, notes, the echoed user text) stays plain text (`ui.label` and `Static(markup=False)`), and `--plain` stays plain text. Raw HTML in the source is never interpreted (`html=False`): it shows as literal text. Images are never rendered or loaded: an image becomes its escaped alt text, because an injected image URL could leak the conversation. Links: `href` only `http`, `https`, `mailto` or a `#fragment`; external links get `rel="noopener noreferrer"` and `target="_blank"`, fragment links get `rel` but no `target`. In the web UI the pipeline is `sanitize_text`, `render_html`, `sanitize_html` (nh3 allowlist, run twice) and `ui.html(content, sanitize=sanitize_html)`: NiceGUI applies a callable `sanitize` on the server and only `sanitize=True` triggers the browser's DOMPurify, so our allowlist is the only filter; never use `ui.markdown`, and never pass `sanitize=True` or `sanitize=False`. The allowlist has no `script`, `style`, `iframe`, `object`, `embed`, `form`, `svg`, `img` or `style` attribute; `class` and `id` values are restricted. In the terminal UI, replies use Textual's `Markdown` widget with `parser_factory` and `open_links=False`. `sanitize_text` removes ESC, control characters other than newline and tab, DEL, C1 controls, bidi controls and the line and paragraph separators U+2028 and U+2029.
- Markdown extensions live in one place, the `_EXTENSIONS` tuple in `src/llm_harness/markdown_render.py` (CommonMark plus tables, strikethrough, linkify, task lists and footnotes); adding one is a one-line change. The terminal UI's Textual `Markdown` widget cannot show task lists (the checkbox is raw inline HTML that Textual drops) or footnotes (Textual raises `IndexError` on footnote tokens), so those two plugins are left out of its parser (`_TEXTUAL_UNSUPPORTED`) and their syntax shows as literal text there. Table column alignment is dropped in the web UI because `style` attributes are not allowed.
- The web GUI has no login. It binds 127.0.0.1 only, rejects any request whose Host or Origin is not `127.0.0.1:<port>` or `localhost:<port>` with HTTP 403, and keeps one chat session per browser client. Never bind another address.
- Front ends show an unexpected exception as the single line `error (unexpected): <Type>: <redacted message>`, never a traceback or local variables; the plain mode prints provider errors as `error (<kind>): <message>`.
- Thinking traces are display-only and never written back into the orchestrator state.
- Persistence: one SQLite file, `~/.local/share/llm-harness/harness.db` (tables `llm_calls` and `model_backoff`), opened with stdlib `sqlite3`. The directory is created with mode 0700 and the file with mode 0600. `store.py` owns the schema version (`PRAGMA user_version`) and its migrations; a file that cannot be used or has a newer version disables the store for the process with one notice, and the file is never deleted or migrated down. Only ids, token counts, costs, times and error kinds are stored, never prompts, replies, error messages or keys. All SQL is parameterized (the one `PRAGMA user_version = N` statement uses an integer the code controls).
- `data_dir` is a keyword of `cli.main` for tests, not a config key; no config key was added for the fallback or the ledger. `tests/conftest.py` has an autouse fixture that sends `store.default_db_path` to a temporary path, so no test touches the real data directory; production code must call it as `store.default_db_path()` through the module for the patch to apply.
- The OpenAI-compatible adapter is verified live against Ollama's `/v1` endpoint; OpenRouter and OpenAI are implemented from documentation and unverified from this machine.
- Every adapter hides the SDK's ambient environment variables while it builds its client (shared helper in `providers/environment.py`): `OPENAI_*` for the OpenAI-compatible adapter, `OLLAMA_API_KEY` and `OLLAMA_HOST` for Ollama, and the `GOOGLE_*` and `GEMINI_*` variables the Google SDK reads for Vertex. `base_url`, `api_key`, `project` and `location` always come from the config.
- Test-only environment variables: `LLM_HARNESS_LIVE_MODEL` (live OpenAI-compatible test) and `LLM_HARNESS_LIVE_VERTEX_MODEL` (live Vertex test). The application never reads them.
- Environment target, Ollama: local Ollama at `http://localhost:11434` is the default dev and test target. The network Ollama host is recorded in the user's home config, not in this repo.
- Environment target, GCP: the dev project and location are recorded in the user's home config, not in this repo. Always pass them explicitly from config, never from ambient environment defaults (no reliance on `GOOGLE_CLOUD_PROJECT` or the gcloud default). Vertex auth uses Application Default Credentials.
- Environment target, database: `~/.local/share/llm-harness/harness.db` is the real ledger; tests and live runs must use a temporary directory (the autouse fixture, or `data_dir`).
- Environment target, OpenAI and OpenRouter: calls are metered and shared; use only small prompts in tests and smoke runs.
- No production target exists.
