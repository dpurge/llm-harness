# Mission

## Problem

There is no hands-on way to find out whether LLMs reached through the Ollama, OpenAI and Vertex AI APIs can be applied to practical tasks at low cost. This project is an LLM coding-agent harness in Python that is used to experiment with those APIs. It is a personal project. Today the harness streams chat over Ollama, OpenAI-compatible APIs and Vertex AI through a plain line mode, a terminal UI and a NiceGUI web UI; a failing model is skipped in favour of the next suitable one and every call's tokens and cost are recorded; every message goes through an orchestrator that keeps a typed state instead of the chat history; the orchestrator can delegate to subagents declared in agents.yaml; the real tools are optional ones: the web tools `web_search` and `web_fetch`, `run_command`, which runs a local program after the human approves it, and the four memory tools.

## Users

The author, on their own hobby projects, as a single developer. The harness is a desktop, interactive application used by one person at a time: it is not a service in a container and not a batch runner. Two interfaces over one shared core: a terminal UI and a NiceGUI web UI.

## Value proposition

Success is that the author uses the harness on their own hobby projects and it works with acceptable reliability on those projects.

The rest of this section describes the goal. What exists today: streaming chat over the three APIs, models declared in configuration with tags and priority, the orchestrator model chosen by tag and priority, per-model prices, fallback to the next suitable model when one fails (with a persisted backoff), a record of tokens and cost per call with a usage line that shows the session total, display of the model's thinking text, and an orchestrator with a typed state (goal, sourced findings, plan, a simple environment block with date and time, user name, computer name and `user_id`) and a reply contract of a state patch plus one action, and a local storage layer (a relational store, SQLite or an optional Postgres server (optional extra `postgres`), a file store and a qdrant-edge vector store, a remote qdrant server (optional extra `remote`) or a pgvector database (optional extra `postgres`), chosen in `[storage]` in `config.toml`; the usage ledger and agent memory use it (agent memory works with either relational store; on Postgres its keyword search uses PostgreSQL full-text search, which may rank differently from SQLite and does not fold accents); the vector store is used only by the optional memory vector index), agents declared in `agents.yaml` with tags (the orchestrator agent's id and tags are used, and any other agent with examples is a subagent the orchestrator can delegate to; the State tab lists them), typed tools with tags in a registry, and the tool `tool_search`, which lets the orchestrator find the tools it may use (every request lists them by name and description), an ask-before-run gate (a tool declares a risk of `read`, `write` or `exec`; before a `write` or `exec` tool runs, the plain mode on a terminal, the terminal UI and the web GUI ask the human and show the exact arguments the tool will receive; with piped input, or in a subagent, the call is denied), two optional web tools, `web_search` (DuckDuckGo HTML, no API key) and `web_fetch` (guarded page fetch with text extraction), switched on in `[tools]`, run without a prompt, with every call's arguments shown to the human as it starts, an optional tool `run_command` (runs one local program from an argv list after the human approves the exact arguments; off by default, switched on in `[tools]`; an allow/deny list and a built-in deny list guard against mistakes and are not a sandbox), and delegation: the orchestrator hands a brief to one subagent, which runs its own short loop with its own tools and a model chosen by its model tags, and gets back a summary with sources; the chat history is not sent to the model, and agent memory (four tools `memory_search`, `memory_save`, `memory_update` and `memory_forget`; automatic recall of the top notes at the start of each turn; a reflection step after work that may save, update or forget a note; the `/memory` command to list, show, delete and reindex notes; keyword search (SQLite FTS5, or PostgreSQL full-text search with a Postgres relational store) with an optional vector (meaning-based) search merged by rank, switched on by `[tools] memory_vectors = true` and falling back to keyword search on any problem; off by default, switched on by `[tools] memory = true` plus a `user_id`). What does not exist yet: real tools beyond the two optional web tools, `run_command` and the memory tools (API and scraper tools, a Docker backend for commands; besides them only `tool_search` and the optional test tool `dev_echo`, switched on by `[tools] dev_echo = true`, exist), nested or parallel delegation, and vector search over memory.

Goal: several APIs and providers are supported so that the author can pick and choose models that are fast and cheap but can do the job. Models are chosen per task from configuration, using tags and priorities (today the orchestrator model is chosen this way, and the user can pick another model by id or in the UI). Today, if the chosen model fails, the next matching model by priority is tried, and tokens and price are tracked per call so the author can see what a call cost; the orchestrator model is chosen by the tag `orchestrator` and priority; a subagent's model is chosen the same way, from its agent's model tags and the model priorities.

Goal: one orchestrator model reads the user prompt, sends work to subagents and assembles the reply. Today the chat history is not sent to the model; the orchestrator's context tracks the user's current goal, the information collected so far with the source of each item, and the plan to reach the goal. The goal may change; the orchestrator tracks the current goal at all times and, if it has no clue what the goal is, asks the user questions. The orchestrator's context always includes the current date and time, the user's name and the computer name. Delegation to one subagent at a time (one level deep) works; still goals: nested or parallel delegation, and recognising the same user on another computer under a different name so that the orchestrator can reach memories about that user.

The author wants good control over context and wants to see it. Today the UIs show streaming thinking traces (reasoning text from models that provide it). The UIs also let the user inspect, at any moment, the orchestrator's current context (a State tab and a Trace tab): the goal, the collected information with sources, the plan, and what will be sent to the model next. Thinking traces are display-only and are never written back into the orchestrator state.

## Non-goals

- Not a production coding assistant.
- Not a replacement for existing general-purpose coding agents.
- No multi-user support and no authentication.
- Not a service in a container and not a batch runner.
- Sending the full chat history to the model: the orchestrator works from its own state instead.
