## Problem / Motivation

The package `src/llm_harness/` is flat: 70 top-level modules mix orchestration, memory (8 files), command execution (5), web tools (5), config and display; file names do not say where a thing belongs. Only `gui/`, `tui/`, `a2ui/`, `providers/`, `storage/` are subpackages. The `tests/` directory is flat (100+ files) with live tests, manual tests and shared fakes beside unit tests.

Turn handling, approval, memory-add flow, model selection and error formatting exist three times (`cli.py`, `tui/app.py`, `gui/app.py`; 13 same-named methods such as `_start_session`, `_approve_call`, `_run_turn`, `_memory_answer`, `_proposer`, `_start_memory_add`, `_run_memory_add`, `_refresh_inspector`, `_end_turn`, `_model_by_id`, `_is_selector_unlocked`, `_turn_is_running`, `_unexpected_error_line`). `gui/app.py` `ChatPage` is one ~540-line class mixing drawing and logic.

Human decisions and assumptions:

- 2026-11-17: work on `main`, never commit (the human commits manually).
- 2026-11-17: keep NiceGUI (the readability pain comes from layout, not the framework); revisiting the GUI framework is deferred until after this feature.
- No import-compatibility shims (human decision): breaking `llm_harness.X` import paths is fine; the only entry point is the `llm-harness` script.
- Old feature specs and old CHANGELOG entries are history and keep their old paths.
- 2026-11-17 (human, plain mode): `chat/session.py`'s `ChatSession` is used by tui and gui; plain (`frontends/cli.py`) keeps its own turn loop and uses only the shared helpers (`MemoryCommands`, `build_orchestrator`, the error/status line helpers). Reason: plain cannot use `ChatSession.start/run_turn` without changing what it does (raw exception text, no catch-all, stops at the first error, streams deltas).
- 2026-11-17 (human, behaviour): the refactor otherwise changes no behaviour, but the human approved fixing exactly three clear bugs found by comparing the three copies, each with a new test: (a) tui ends the turn at the `Done`/`ErrorEvent` event and never re-enables the prompt when the stream ends with neither, so tui ends the turn in a `finally` like gui; (b) gui sends `/exit` to the model while tui and plain quit, so gui treats `/exit` as quit like tui and plain; (c) gui and plain approval prompts do not sanitize the tool and agent names while tui does, so gui and plain sanitize them with `sanitize_text` like tui. All other differences between the copies are preserved (see Implementation Notes).

## Acceptance Criteria

1. Behaviour is identical: the full offline test suite (`uv run pytest`, live tests deselected) has the same pass count as the baseline recorded at the start, with no new skips.
2. No module remains directly under `src/llm_harness/` except `__init__.py` (and the entry module if kept at `frontends/cli.py`, then the pyproject script is `llm-harness = "llm_harness.frontends.cli:main"`).
3. The layout is exactly:
   - `config/` (config, secrets_file, pathing)
   - `core/` (types, state, state_io, state_files, context, orchestrator, subagents, trace, approval, inspect_state, redact, display, block_text)
   - `models/` (providers/, router, routing, store as ledger, embeddings)
   - `tools/` (registry from tools.py, builtin_tools, `web/` {url_guard, fetcher, extract, search, tools}, `command/` {policy, executor, docker_command, docker_executor, tool})
   - `memory/` (store from memory.py, add, command, file, index, recall, reflection, tools, transfer; the `memory_` prefix dropped)
   - `chat/` (session.py, commands.py)
   - `frontends/` (cli.py, plain/, tui/, gui/, markdown_render.py)
   - `storage/` and `a2ui/` unchanged; `prompts/` unchanged at the package root.
4. Front-end-only dependencies (nicegui, textual, starlette) are imported only under `frontends/` (checked by grep and pinned by a test); `core`, `config`, `models`, `tools`, `memory`, `chat` and `a2ui` import none of them.
5. `chat/session.py` holds the turn, approval, memory-add, model-select and error-formatting logic and is used by tui and gui; plain uses the shared helpers; the 13 duplicated methods no longer exist in three copies (grep evidence checked for tui, gui and plain).
6. `gui/` is split so that `ChatPage` drawing lives in widgets and logic in the session (a file per concern, file names say what is inside).
7. `tests/` mirrors `src/`: `tests/core`, `tests/tools`, `tests/memory`, `tests/models`, `tests/chat`, `tests/frontends/{plain,tui,gui}`, `tests/a2ui`, `tests/storage`, `tests/config`; live tests under `tests/live/`, shared fakes under `tests/support/`.
8. Packaged prompts still load from an installed wheel (build the wheel, assert `prompts/*.md` are in it).
9. README, the `specs/tech-stack.md` Layout bullet and the stale CHANGELOG line that names `src/llm_harness/session.py` are updated.
10. Every moved or new function has a non-test call site (grep evidence).
11. Windows-safe: no POSIX-only code added; paths via `pathlib`.
12. Each of the three approved fixes has a test: (a) tui ends the turn in a `finally`; (b) gui treats `/exit` as quit; (c) gui and plain approval prompts sanitize the tool and agent names with `sanitize_text`.

## Approach

Memory consulted: grep -i "gui|layout|refactor|package" memory.md — 14 relevant entries (NiceGUI test-fixture gotchas: string-target monkeypatch.setattr("llm_harness.x.Y") raises AttributeError after the nicegui user fixture teardown, so patch module objects; test doubles standing in for Orchestrator must accept every Orchestrator.__init__ keyword incl. user_id= and storage=; pytest needs -p nicegui.testing.user_plugin)

Key decisions and alternatives considered:

- (a) Restructure plus a shared `ChatSession`: chosen.
- (b) Switch the GUI to a webview plus JS-component stack: rejected for now. The constitution says no JS/Node, it would be a GUI rewrite of ~4,000 lines plus ~4,500 test lines, and the TUI would remain a second front end.
- (c) Move files only, without extracting the session: rejected; the duplication is the hidden-logic problem.

Known facts from the survey:

- No module-level import cycles; two lazy-import cycle breakers (`config.py:846` secrets_file; `orchestrator.py:795` subagents) must stay valid after the move.
- `storage/__init__.py` eagerly imports all backends.
- 11 test files import `cli`; 6 test files use quoted `"llm_harness.x"` string targets and 15 patch module objects, so each move step must update them.
- The prompt loader `memory_reflection.py:224` uses `files("llm_harness")/"prompts"`.
- The loaders of `subagent.md` and `memory_add.md` are not yet located: find them in step 1 and note them in Implementation Notes.

Ordered plan; each step ends with the full offline test run and a short report to the human before the next:

0. Baseline run (record counts).
1. `frontends/` (cli, plain, tui, gui, markdown_render) and the pyproject script.
2. `config/`, `core/`, `models/`.
3. `tools/` and `memory/`.
4. Tests mirror `src/` (move only, no logic change).
5. Extract `chat/session.py`, one front end per sub-step: 5a tui (with fix a), 5b gui (with fixes b and c), 5c plain (helpers only, with fix c). Design (from the read-only architect, unverified by running code): module `chat/session.py` (no framework imports) with helpers `unexpected_error_line`, `error_event_line`, `status_text`, `build_orchestrator`, `is_approval_yes`; `MemoryCommands` (owns pending proposals, `answer`, `proposer`); a `TurnView` Protocol the front end implements to render; `ChatSession` (start, is_selector_unlocked, model_by_id, new_chat_is_manual, run_turn, run_memory_add, aclose); `commands.py` moves to `chat/commands.py` in 5a; the front end keeps scheduling the turn (Textual Worker / asyncio.Task), approval prompts, widgets and a2ui drawing; tui keeps /export and /import. Non-regression is the existing suite (5164 passed baseline plus new tests); no extra before/after scripts.
6. Split the gui `ChatPage` into a widgets module and logic.
7. Docs.

Moves use plain `mv` (or staging-free moves); the agent does not commit, push or branch; the human commits manually. Step 5 is the only step with a risk of behaviour change; if it needs more than the described extraction (new public behaviour, changed prompts, changed error text), stop and re-approve.

Testing strategy: offline suite only (no live tests, no real model calls). New tests: an import-boundary test (front-end deps only under `frontends/`), session unit tests with the scripted fake provider, and a wheel-contents test.
