## Problem / Motivation

Memories live only in the relational store (SQLite file or a Postgres server). The human has no way to take a copy of their notes, move them to another machine or another `user_id`, or restore them after a mistake: the `/memory` verbs list, show, search, delete, publish, unpublish, forget, reindex and add (`src/llm_harness/memory_command.py:41-55`) read, remove or create notes one at a time. The only file transfer that exists is `/export` and `/import` of the ORCHESTRATOR STATE, a different thing, available in the TUI only (`src/llm_harness/state_files.py:21-22`, `:43-54`). The roadmap item `memory-yaml-transfer` (`specs/roadmap.md:15`) asks for it; `memory-add-command` (done) names it as a separate item.

Human decisions (2026-11-04, recorded as decided):

- Two new commands: `/memory export [--shared] [PATH]` writes your memories to a YAML file; `/memory import [--shared] PATH` reads them from one.
- SLASH COMMANDS ONLY, in all three front ends (CLI plain mode, TUI, web GUI). Explicitly NO GUI buttons and no upload or download widgets (the human repeated this). The path is on the machine that runs the harness; the GUI runs locally on 127.0.0.1, as with `/memory add @FILE`.
- Admins (a `user_id` listed in `[tools] memory_admins`) may `/memory import --shared PATH`; the admin check runs BEFORE the file is read. `/memory export --shared` includes the shared notes and is admin only.
- Import is IMMEDIATE and answers with counts. There is no preview and no confirm step.
- An exported entry holds the text and keywords AND the ids and timestamps (a faithful backup). The human was told this costs more: import must not lose the timestamps through the injected clock (see Approach, timestamp preservation).
- These commands are separate from the existing `/export` and `/import` of orchestrator state (TUI only). The answers and the README say so.
- Future-dated timestamps are rejected (human, 2026-11-04: "Reject dates in the future. Just implement it"): the store refuses them, and an import entry whose timestamp pair is bad or future gets the current time and is counted (see Approach, timestamp preservation).
- Missing timestamps (human, 2026-11-04: "If import data is missing a timestamp, use current date time"): `created` and `updated` are OPTIONAL per entry; a missing one (or both) takes the current time silently, with no note in the answer. Only a bad value counts (see Approach, timestamp preservation).

Assumptions (the human may change them):

- (a) Forms. `/memory export [--shared] [PATH]`: no PATH means `llm-harness-memories.yaml` in the current directory (the state export's default is `llm-harness-state.yaml`, `src/llm_harness/state_io.py:17`; `resolve_path` returns THAT name for an empty argument, `src/llm_harness/state_files.py:57-61`, so the memory command builds its own default and never passes an empty argument to `resolve_path`). `/memory import [--shared] PATH`: PATH is required, else usage. PATH is the rest of the line as typed, spaces allowed, stripped, `~` expanded through `resolve_path`; a `~user` of an unknown user raises `RuntimeError`, which the command turns into a refusal like `read_text_file` does (`src/llm_harness/memory_file.py:75-78`). A path literally named `--shared` is written `./--shared` (a leading `--shared` is the flag). `--shared` counts only as the FIRST word after the verb (the same rule as `add`, `_parse_add`, `memory_command.py:111-130`). `MemoryCommand` gets the actions `export` and `import`; `query` holds the path as typed and `shared` the flag (existing fields, `memory_command.py:65-75`).
- (b) File format. A top-level mapping: `version: 1`, `exported: <UTC timestamp>` (informational, optional on import), `memories:` a list of mappings with `id` (int, informational, ignored on import), `text`, `keywords` (list of strings), `created`, `updated` (strings in the store's timestamp format; both OPTIONAL on import, an absent key is valid and is filled as in Approach (both absent: the current time; one absent: it copies the other), while `text` and `keywords` stay required), and `shared: true` ONLY for a shared note (the key is absent otherwise). Written with `yaml.safe_dump(..., allow_unicode=True, sort_keys=False)`, exactly the options `export_yaml` uses (`state_io.py:60-67`; pyyaml 6.0.3 installed, declared `pyyaml>=6.0.3`, `pyproject.toml:20`). Verified by a run: `safe_dump` writes a timestamp string such as `2026-11-04T10:00:00Z` QUOTED (`created: '2026-11-04T10:00:00Z'`), so it round-trips as a string; an UNQUOTED hand-written timestamp loads as a `datetime`, not a string (see (d)). Entries are written in ascending `id` order. Unknown top-level keys or unknown entry keys reject the whole file with one safe line; so does any `user_id`-like key (the file carries no user). A `version` other than 1 gives `unsupported memories file version N` (N only when it is an int, else `unsupported memories file version`).
- (c) Export. Only the caller's OWN notes by default (`memory.user_id == user_id`, an own note that is published is included and marked `shared: true`). `--shared` (admin only, checked first, a non-admin never causes a store call) adds the shared notes of everyone. A new constant `NOT_ADMIN_EXPORT = "only memory admins may export shared memories"`, next to `NOT_ADMIN` (`memory_command.py:205`), `NOT_ADMIN_FORGET` (`:234`) and `NOT_ADMIN_ADD` (`:313`): a separate constant per refusal, like those three. The notes come from `store.list(user_id, limit=_LIST_ALL)` (`memory.py:501-512`, `_LIST_ALL` at `memory_command.py:58`) filtered in the command, then sorted by id. The file is created through `write_export` (`state_files.py:72-95`: parent must exist, a directory is refused, `O_WRONLY | O_CREAT | O_EXCL | O_NOFOLLOW`, mode `0o600` at `:81-83`, never overwrites, an existing path answers `<path> already exists`, a failed write removes the half file). Answer: `exported N memories to <escaped path>`. Zero notes: the command refuses with `no memories to export` and creates no file (decision: an empty file would look like a backup and is not one). `write_export` blocks, so it runs in `asyncio.to_thread`. More than 200 notes are still written, and the answer adds `; import takes at most 200 per file` (decision: a backup must not be refused; the human may prefer a split).
- (d) Import. The order is fixed: parse, memory gate, the `--shared` admin check, THEN any filesystem access, then size, decode, parse, then the saves. Reading reuses `read_import` (`state_files.py:98-117`: `os.stat` regular-file check, `O_RDONLY | O_NONBLOCK`, `fstat` check on the descriptor, size from `fstat` checked BEFORE reading, read at most `MAX_IMPORT_BYTES + 1`, a second size check) and NOT `read_text_file` (decision and reason: `read_text_file` is built for text notes, with a 64 KB cap, a mandatory `.txt`/`.md`/`.markdown` extension and a 4000-character check, `memory_file.py:17-19`, `:66-90`, none of which fits a YAML file of up to 1 MB; its stat, regular-file and `O_NONBLOCK` steps are the same ones `read_import` already has, so reusing them is not needed and a third copy is avoided). `read_import` errors never contain the path (class name and `strerror` only, `_os_reason`, `state_files.py:64-69`). Cap `MAX_IMPORT_BYTES` = 1,000,000 bytes (`state_io.py:16`; error `file is larger than 1000000 bytes` from `check_size`, `:70-73`). Strict UTF-8 (`file is not UTF-8 text`, as `import_yaml`, `:79-82`). Parsed with the no-alias loader (`_NoAliasLoader`, `state_io.py:28-39`), so aliases are refused (`YAML aliases are not supported`), a YAML error gives `not valid YAML (or uses an unsupported tag)`, and `RecursionError` gives `YAML is nested too deeply` (`:83-89`). The new parser reuses `_NoAliasLoader` through a public alias or a move to a shared name (decide at implementation; do not copy it). At most 200 entries (`too many memories (N, at most 200); split the file`). Each entry's `text` and `keywords` go through `validate_note` (`memory.py:281-286`: trims, 1 to 1500 characters, no control characters, secret-free, 1 to 8 distinct lowercase keywords). An entry that fails is SKIPPED and counted as rejected; its text, keywords and the store's message are never echoed (the keyword message quotes up to 30 characters, `memory.py:266-270`). A duplicate (`has_text(user_id, text)`: the caller's own note or any shared note, `memory.py:382-390`) is skipped and counted as known; the schema has no UNIQUE constraint on text (`memory.py:33-91`), so `has_text` is the only guard and two identical entries in ONE file are caught because saves are sequential. Imported notes belong to the importing user (`user_id` = caller). `id` is ignored: new ids are assigned (on Postgres `id` is `GENERATED ALWAYS AS IDENTITY`, `memory.py:102`, so an explicit id could not be inserted anyway). `shared: true` entries become shared ONLY with `--shared` by an admin; otherwise they are imported as PERSONAL notes and the answer says how many. Structural errors reject the file with one safe line built from a fixed phrase, never from the file's values: top level not a mapping, `memories` missing or not a list, an entry not a mapping, `text` not a string, `keywords` not a list, `id` not an int (a bool is not an int), `shared` not a bool. A `created` or `updated` value that is not a string in the store's format (an unquoted YAML timestamp loads as a `datetime`) is not a file error; it is handled as a bad timestamp (Approach). An ABSENT `created` or `updated` key is neither an error nor a bad timestamp: it is filled silently (both absent: the current time; one absent: it copies the other). `text` and `keywords` stay required: a missing `text` is a structural error (`text` not a string) and a missing `keywords` is a structural error (`keywords` not a list).
- (e) Counts. Answer: `imported N of M memories; skipped K already known; rejected J invalid`, then, only when non-zero, `; X shared entries imported as personal` and `; Y entries got the current time (bad or future timestamps)`; Y counts only entries with a bad or future pair, never entries whose timestamps are merely missing. Counts are not pluralised, like the add answers (`saved 1 of 1 memories`). M is the number of entries in the file.
- (f) Index cost. `IndexedMemoryStore.save` embeds the note right after the SQL insert (`src/llm_harness/memory_index.py:169-178`, `_index` at `:332`), so with vector search on, an import of 200 notes is up to 200 sequential embedding calls. Hence the 200 cap. A failing embedder does not fail the import: `_guarded` turns the index off with a one-time notice and the SQL rows stay (`memory_index.py:335-344`); the notice is appended by `handle_memory_text` as for every `/memory` answer (`memory_command.py:553`). A batch path exists in the index (`_index_batch`, `:300`, used by reindex); using it for import is a possible later optimisation and is NOT part of this spec.
- (g) Cancellation. Import and export run in the same task slot as a normal turn, so Escape (TUI) and Stop (GUI) cancel them, as for `/memory add` (`gui/app.py:393-394`, `_start_memory_add` at `:438`; `tui/app.py:308-309`, `_start_memory_add` at `:352`). A cancelled import reports no counts; the notes already saved stay in the store (each save is its own statement; there is no transaction around the import) and running the same import again skips them as known and keeps their timestamps. A thread already started by `asyncio.to_thread` cannot be interrupted: a cancelled export may still finish writing its file, and a cancelled import discards the parsed result. The front ends show their existing `cancelled` line and restore the typed text (the add test pattern, `tests/test_gui.py:1854-1875`).
- (h) `memory = true` and a `user_id` are required, else the existing `MEMORY_OFF` answer (`memory_command.py:39`, `:535-536`). Vector search is not required.
- (i) Pending state: none (immediate).
- (j) `USAGE` and the `/memory` COMMANDS entry gain `export [--shared] [PATH]` and `import [--shared] PATH` (`memory_command.py:41-55`, `src/llm_harness/commands.py:46-53`); `/help memory` still equals `USAGE` because the detail IS `MEMORY_USAGE`.
- (k) Tool safety: no memory tool and no reflection step gains an export or import path, and no tool can pass the timestamp arguments of the new store write path. Pinned by tests like the existing `forget_shared` ones (`tests/test_memory_tools.py`, the two pins named in `specs/features/memory-shared-admin.md`, Implementation Notes).
- (l) YAML is untrusted input: safe loader without aliases or custom tags, size and entry caps, a strict key set, every text validated. Verified by a run on 2026-11-04 with pyyaml 6.0.3 and `_NoAliasLoader`: `[` repeated 200000 times (200000 bytes) raised `RecursionError` in 0.54 s, 2000 nested block sequences (about 2 MB) and 1500 nested block mappings (about 1.1 MB) raised `RecursionError` in under 0.1 s each, so `import_yaml`'s `except RecursionError` (`state_io.py:88-89`) turns a nesting bomb into a one-line refusal without a hang. NOT verified: the same inputs inside a worker thread (a thread's C stack is smaller than the main thread's on some platforms); the test of criterion 12 runs it in a thread.
- (m) Privacy: an exported file holds the user's notes in CLEAR TEXT. Mode `0600` keeps other local users out, but the content is plain, so the README says to treat the file like the database. The exported file contains no `user_id`. Export and import call no chat model; with vector search on, import sends each imported note's text to the embedding model, as every save does.

## Acceptance Criteria

Two steps. Criteria 1 to 14 belong to step 1 (the pure module and the store write path; offline unit tests); criteria 15 to 34 belong to step 2 (commands and front ends). All run OFFLINE: a real `SqliteRelationalStore` on `tmp_path` (the `storage` fixture of `tests/test_memory_add_command.py:135-142`), `FakeVectorStore` and the `Rig` of `tests/test_memory_index_store.py` for the indexed store, `tmp_path` files, and no model at all (no `ScriptedProvider` needed, `propose` stays None). No live model and no live PostgreSQL run is required.

1. **Format: the writer and reader round trip.** `export_memories(memories, exported_at)` then `parse_memories_file(bytes)` returns entries equal to the input in text (including a non-ASCII text), keywords, `created`, `updated` and the `shared` marker; `id` is carried but flagged informational; the output starts with `version: 1`; timestamps are written as quoted strings; `shared` appears only for a shared note; entries are in ascending id order.
2. **Format: the file shape.** The written file loads with plain `yaml.safe_load` into the documented mapping (keys `version`, `exported`, `memories`; entry keys `id`, `text`, `keywords`, `created`, `updated`, optional `shared`), and contains no `user_id`.
3. **Parse: refusals of the whole file.** `parse_memories_file` raises the typed error (a `ValueError` subclass, one safe line, no newline) with the exact message for: over 1,000,000 bytes (`file is larger than 1000000 bytes`), bytes that are not UTF-8, invalid YAML, an alias, a tag such as `!!python/object`, top level not a mapping, `version` missing, `version: 2` (`unsupported memories file version 2`), a non-int version, an unknown top-level key, an unknown entry key, a `user_id` entry key, `memories` not a list, an entry not a mapping, `text` not a string, `keywords` not a list, `id` not an int (and `id: true`), `shared` not a bool, and 201 entries (`too many memories (201, at most 200); split the file`); exactly 200 entries parse. No message contains a value from the file.
4. **Parse: a nesting bomb.** `[` repeated 200000 times and a deeply nested block structure each give `YAML is nested too deeply` quickly (the test also runs once inside `asyncio.to_thread`, assumption (l)); an alias bomb of a few hundred bytes gives the alias refusal in well under a second.
5. **Parse: entries are passed on raw.** An entry whose text is secret-looking, two-line or empty still parses (the per-entry check belongs to the import step, criterion 20); `created`/`updated` of any YAML type (a string, an unquoted `datetime`, an int, a missing key) parse without error and are returned as given or as None.
6. **Store: timestamp-preserving save.** `MemoryStore.save(user_id, text, keywords, shared=False, *, created_at=None, updated_at=None)` with both given in the store's format stores exactly those values (the `Memory` returned and a fresh `get` agree); without them the injected clock still decides both (`created_at == updated_at ==` the clock value), so the old callers are unchanged; giving only one of the two copies it to the other (`created_at` given alone also becomes `updated_at`, and the reverse), so `updated` is never earlier than `created`; with both given, `updated_at` earlier than `created_at` is refused.
7. **Store: strict timestamp validation, future refused.** A `created_at` or `updated_at` that is not `YYYY-MM-DDTHH:MM:SSZ` (lowercase `t`, a `+00:00` offset, a date only, fractional seconds, a trailing space, a non-string) or is LATER than the injected clock now raises `MemoryValidationError` (the store validates itself, not only the command; `None` is not a bad value, it means absent: both absent take the clock value, one absent copies the other, criterion 6; a lone given value is still validated, so a future lone value is refused); a value equal to now is accepted; the message never echoes the value. The `list` order of two notes follows the preserved `updated_at`, and a far-future value cannot pin a note at the top.
8. **Store: the schema machinery sees an explicit-timestamp insert like any insert.** On SQLite, after a `save` with explicit timestamps the note is found by `search` (the `memories_ai` trigger indexed text and keywords, `memory.py:49-52`, and it never reads the timestamps), no `memory_vectors` row exists for it (the marker table has triggers only on UPDATE of text or keywords and on DELETE, `memory.py:78-84`), and a later `update` of its text still clears a marker as before; `shared=True` with explicit timestamps stores `shared = 1`.
9. **Store: Postgres statement text.** On the Postgres fake of `tests/test_memory_postgres.py`, a save with explicit timestamps issues the same single `INSERT INTO memories (user_id, text, keywords, created_at, updated_at, shared) ... RETURNING` statement with the explicit values as parameters, and a save without them binds the clock value twice as before. The statement run against a real PostgreSQL server is NOT done (unverified, see Validation notes at the end of the work).
10. **Indexed store passes the timestamps and embeds once.** `IndexedMemoryStore.save(..., created_at=..., updated_at=...)` stores the given timestamps and makes exactly ONE embedding call and one vector upsert per saved note (`FakeVectorStore` call log), writing the usual payload.
11. **Indexed store: a failing embedder.** With an embedder that raises, `IndexedMemoryStore.save` with explicit timestamps still returns the note, the SQL row exists with the preserved timestamps, `index_off_reason` is set, `take_notice()` reports once, and the next saves make no embedding call.
12. **Memory timestamps helper.** A public `MemoryStore` method returns the current timestamp in the store's format from the injected clock (for the `exported` header), and a fixed clock gives a fixed header string; the parse of a file with an unquoted timestamp does not raise.
13. **Tool safety (store level).** `created_at=` and `updated_at=` as arguments to `save` occur only in `llm_harness.memory`, `llm_harness.memory_index`, `llm_harness.memory_command` and `llm_harness.memory_transfer`; the `memory_save` tool input schema has no such property (like the existing `shared` pin, `tests/test_memory_tools.py`).
14. **Round trip through the store.** Export of a store with private and shared notes of two users, then import into an EMPTY store as another user, gives notes with equal text, keywords, `created_at` and `updated_at` and new ids; the order of `list` by `updated_at` is the same as in the source.
15. **Parse: the transfer forms.** `parse_memory_command` gives `MemoryCommand("export")` for `/memory export` (empty path), `MemoryCommand("export", query="/tmp/a.yaml")` for `/memory export /tmp/a.yaml`, `shared=True` for `/memory export --shared` and `/memory export --shared /tmp/a.yaml`, `MemoryCommand("import", query="/tmp/a.yaml")` for `/memory import /tmp/a.yaml`, `shared=True` and the path `~/my notes.yaml` (spaces kept, stripped) for `/memory import --shared ~/my notes.yaml`; usage for `/memory import` and `/memory import --shared` (no path); `/memory export ./--shared` exports to the path `./--shared` (not the flag); a `--shared` AFTER the first word is part of the path; spacing inside the path is kept as typed.
16. **Command: memory off.** With memory off (no storage, no `user_id`, or no memory tool) both commands answer `MEMORY_OFF` before any filesystem access (a loader spy and a writer spy are never called).
17. **Command: export writes a faithful 0600 file.** For a user with two own notes (one published by an admin), `/memory export <tmp path>` answers `exported 2 memories to <path>`, the file exists with mode exactly `0o600` (`stat`), its content parses back to the same notes, it holds no other user's private note and no shared note of another user; `/memory export` without a path writes `llm-harness-memories.yaml` in the current directory (the test changes the working directory to `tmp_path`).
18. **Command: export never overwrites and refuses bad targets.** An existing file (including a dangling symlink and a symlink to a file) answers `<escaped path> already exists` and the file content is unchanged; a missing parent directory and a directory as the path answer the one-line `write_export` refusals; zero notes answers `no memories to export` and creates no file; 201 notes write the file and the answer ends with `; import takes at most 200 per file`.
19. **Command: `--shared` needs an admin, before any store or filesystem access.** For a non-admin and for an empty `memory_admins`, `/memory export --shared <path>` answers `NOT_ADMIN_EXPORT` and `/memory import --shared <path>` answers `NOT_ADMIN_IMPORT` (new constants, wording as in assumption (c)), the reader and writer spies are never called, the path is not touched (it does not exist and no error about it is shown), and the store spy records no call. For an admin, `export --shared` includes the shared notes of everyone, each marked `shared: true`, and the answer counts them.
20. **Command: import saves and counts.** `/memory import <file>` of a file of 5 entries answers `imported 5 of 5 memories; skipped 0 already known; rejected 0 invalid`; the notes belong to the importing user (another user does not see them, `/memory list` of the importer shows them), have NEW ids, the file's `created`/`updated` values, and the `id` field of the file is ignored; the answer carries no text of any note.
21. **Command: per-entry skips, no echo.** A file mixing a valid entry, a duplicate of the importer's own note, a duplicate of a shared note of another user, two identical entries (the second is skipped), a secret-looking entry (an API-key-shaped string), a two-line text, an over-long text and a bad keyword answers the exact counts (`imported 2 of 8 ...; skipped 3 already known; rejected 3 invalid` or the counts the fixture gives); the secret text and the bad keyword appear nowhere in the answer, and nothing of them is in the store.
22. **Command: shared entries become personal without `--shared`.** Importing a file with 2 `shared: true` entries as a non-admin and as an admin WITHOUT `--shared` stores personal notes (`shared = 0`) and the answer ends with `; 2 shared entries imported as personal`; the same file as an admin WITH `--shared` stores shared notes (another user sees them marked `[shared]` in `/memory list`) and has no such suffix; entries without the marker stay personal in both cases.
23. **Command: timestamps kept, missing ones filled silently, bad or future ones replaced and counted.** Entries with valid past timestamps keep them; an entry with a future `updated`, a malformed `created`, an unquoted YAML timestamp, or `updated` earlier than `created` gets the clock time for both (the injected clock) and is saved, and the answer ends with `; N entries got the current time (bad or future timestamps)` with N counting exactly those entries; with only valid or missing timestamps the suffix is absent. Missing timestamps are not bad: an entry with both `created` and `updated` missing gets the clock value for both, an entry with only `created` missing keeps its valid `updated` and copies it to `created`, an entry with only `updated` missing keeps its valid `created` and copies it to `updated`; all three are saved, and the answer of a file holding only such entries shows no timestamp note.
24. **Command: each file refusal reaches the user as one line with no model or store write.** For a missing file, a directory, a FIFO (the test does not hang), a file over 1,000,000 bytes (refused from `fstat` before reading), a file that is not UTF-8, invalid YAML, an alias, a wrong version, an unknown key, wrong types and 201 entries, the answer is the single line of the matching refusal; nothing is saved (`list` unchanged); a hostile path (newline, ESC and a bidi character in the name, created under `tmp_path` where the platform allows, else passed as a missing path) never appears raw in any answer: the success line of an export shows it through `escape_text` (`\uXXXX`) and the other messages do not contain the path at all.
25. **Command: threading and order.** A reader spy, a parse spy and a writer spy each record `threading.get_ident()` different from the event loop thread's; for `import --shared` the admin check precedes the read (criterion 19), and the read and parse finish before the first save.
26. **Command: cancel.** Cancelling the task awaiting an import (a store whose `save` blocks after the first note) raises `CancelledError`, leaves the first note saved and no further one, shows no counts, and running the import again skips the saved note as known and imports the rest with their timestamps; cancelling an export leaves no half file except one that a thread already wrote completely (the test asserts that the file is either absent or complete and parses).
27. **Command: indexed store cost and failure.** On an `IndexedMemoryStore` through `handle_memory_text`, an import of 3 entries makes 3 embedding calls (one per saved note, none for skipped ones); with a failing embedder the answer still has the counts, the SQL rows exist with their timestamps, and the one-time index-off notice is appended to the answer.
28. **Front ends: the GUI is primary and mandatory.** A NiceGUI `User` test in `tests/test_gui.py`, like `test_memory_publish_in_the_gui_needs_an_admin` (`:1650`), `test_memory_add_in_the_gui_reads_a_markdown_file` (`:1796`) and `ask_memory` (`:1634`, which types into the `prompt` marker and waits for the NEW `memory` answer element): the test types `/memory export <tmp path>` and sees `exported N memories to <path>`, then, as another user (a second page or a second store seeded from the exported file, so that the file is imported by a user who does not own the notes; how a second `user_id` is arranged with `memory_front_end(tmp_path, user_id, admins)`, `:1613`, is decided at implementation), types `/memory import <same file>` and sees the `imported ...` counts; the list then shows the notes; no `user` turn element is created, no model request is made, and no upload or download element exists on the page (the test asserts that the page has no `upload` element and no export or import button besides the existing state buttons).
29. **Front ends: GUI Stop.** A GUI test with a store whose `save` blocks (slow store) types `/memory import <file>`, presses Stop while the controls are busy, checks that the controls are enabled again, `cancelled` is shown, the typed text is restored, and a later `/memory` lists only the notes saved before Stop (pattern of `:1854-1875`); if a slow store cannot be injected through `register_page` the test is replaced by a unit test of criterion 26 and the gap is stated in Validation.
30. **Front ends: TUI.** The TUI test (like `test_memory_publish_in_the_tui_needs_an_admin`, `tests/test_tui.py:1245`, answers read from the `note` elements) covers export to a `tmp_path` file, import of it, `--shared` refused for a non-admin, a refused file, and an Escape that cancels a blocking import with `cancelled` shown; both commands run in the `turn` worker group, not inline.

## Approach

Memory consulted: grep of specs/memory.md for `yaml|export|import|timestamp|clock|save|nicegui|patch` — 5 relevant entries (lines 22, 28, 29, 64, 65): pyyaml 6.0.3 `safe_load` expands aliases by reference and `state_io.py` parses with a `SafeLoader` subclass that rejects them (hence the no-alias loader for the memories file); `write_export`'s `O_EXCL | O_NOFOLLOW | 0600` open refuses an existing file, a symlink and a dangling symlink; `read_import` opens with `O_NONBLOCK` and checks `S_ISREG` on the descriptor so a FIFO does not hang; tests must patch a module through the imported module object (`monkeypatch.setattr(module, name, value)`), and the nicegui `user` fixture teardown pops `llm_harness.gui.app` from `sys.modules` (relevant to the GUI tests).

An ordered plan of exactly two implementation steps, each ending with green tests.

STEP 1: the pure YAML module and the timestamp-preserving store write path.

1. `src/llm_harness/memory_transfer.py` (new, pure, no I/O): `FORMAT_VERSION = 1`, `MAX_ENTRIES = 200`, `MEMORIES_FILENAME = "llm-harness-memories.yaml"`, the typed error `MemoriesFileError(ValueError)`, `TransferEntry` (text, keywords, created, updated, shared, id; raw values), `export_memories(memories, exported_at) -> bytes` (`yaml.safe_dump(..., allow_unicode=True, sort_keys=False)`, entries in ascending id, `shared` only when true), and `parse_memories_file(data: bytes) -> list[TransferEntry]` (size check through `state_io.check_size`, strict UTF-8, the no-alias loader of `state_io.py:28-39`, `RecursionError` mapped to `YAML is nested too deeply`, the key sets and structural checks of assumption (d), the 200 cap). Error messages are fixed phrases, never built from file values; `StateImportError` from the shared loader and `check_size` is re-raised as `MemoriesFileError` (or the module catches it; decide at implementation) so the command catches one type. The loader is reused, not copied.
2. `src/llm_harness/memory.py`: timestamp preservation, designed as follows (the design the human asked about).
   - `MemoryStore.save(user_id, text, keywords, shared=False, *, created_at=None, updated_at=None)`: the two new parameters are keyword-only and default to None, and in that case the code path is the existing one: `now = self._now()` for both (`memory.py:367`, `_now` at `:533`), so every current caller and the injected clock stay the default and nothing changes for tools, the reflection or `/memory add`. When given, each value is validated BY THE STORE (not only by the command) with a new public helper `check_timestamp(value, now)` in `memory.py`: it must be a `str` that matches the store's format exactly, `YYYY-MM-DDTHH:MM:SSZ` (the `_TIMESTAMP_FORMAT` of `memory.py:150`, checked with a fullmatch regex of digits and a real `strptime` parse so `2026-02-30T...` fails), and must not be LATER than `now`, the injected clock at the moment of the save. Both missing (None): both take the clock value, silently. Only one given: the missing one copies it (coordinator ruling, 2026-11-04, made for the human on a Step 1 engineer finding: taking the clock for a missing `created` would give `updated` < `created`, which is refused, and a missing timestamp would become an error; a given value is still validated, so a future lone value is refused). `updated_at` earlier than `created_at`, both given, is refused. Failures raise `MemoryValidationError` with a fixed message that never echoes the value.
   - Why future-dated values are refused: `list` and the recall order by `updated_at DESC` (`memory.py:501-512`), and `update` writes `self._now()` (`memory.py:417`); a far-future `updated_at` would sort a note first in every listing and in recall until the clock reached it, and the next `update` would only fix it if the owner touched the note. The comparison is on the same string format, which sorts like time (`memory-format` skill rationale, same format). A file from another machine with a clock ahead of this one gets the current time instead, and the answer says so; that is the cost and it is stated in the answer.
   - Why the lower bound is open: an old timestamp only sorts a note lower; it cannot hurt other notes, so any valid past value is kept.
   - The command (step 2) applies the SAME rules before calling `save`, through `check_timestamp`, so it can count a replaced pair instead of letting the store raise; a MISSING `created` or `updated` is passed as None (both missing: the clock; one missing: it copies the other) and is not counted; only a malformed value, a future value, an unquoted YAML timestamp (a `datetime`) or `updated` earlier than `created` makes the pair bad, and then it calls `save` without timestamps (the clock decides both) and counts it. The store check stays as defence in depth and is the only thing that matters for a caller other than the command.
   - `IndexedMemoryStore.save` (`memory_index.py:169-178`) gains the same two keyword-only parameters and forwards them; the embedding and the payload do not read timestamps.
   - Schema: no migration. `memories.created_at` and `updated_at` are plain `TEXT NOT NULL` columns on both dialects (`memory.py:40-41`, `:106-107`) and the INSERT already lists them; only the bound values change. The id column is NOT inserted (a new id, and Postgres `GENERATED ALWAYS` would refuse one, `:102`). Verified in the code: `memories_ai AFTER INSERT` (`:49-52`) fires for any INSERT and only copies `text` and `keywords` into the FTS table, `memories_vectors_stale` fires on `UPDATE OF text, keywords` only (`:78-81`), and the marker table has no INSERT trigger, so a new row simply has no marker until `IndexedMemoryStore` embeds it. On Postgres the FTS column is a generated column (`:108-110`), unaffected. Criterion 8 proves the SQLite part by a run; the Postgres part is statement text only (criterion 9).
   - A public `MemoryStore` method returns the current timestamp string from the injected clock for the `exported` header, so the command never calls the private `_now`.
3. Tests: criteria 1 to 14 (`tests/test_memory_transfer.py` new; additions in `tests/test_memory_store.py`, `tests/test_memory_postgres.py`, `tests/test_memory_index_store.py`, `tests/test_memory_tools.py`).

Risks, inside the approach:

- Timestamp pinning and the clock bypass. This feature adds the first write path that lets a caller choose `created_at`/`updated_at`. Mitigation: keyword-only, default None, validated by the store itself, no future values, the pin of criterion 13 keeps every tool and the reflection away from it. A caller inside the harness code could still backdate a note (a past value is allowed by design); only the command passes timestamps.
- A far-future or malformed timestamp in a hand-edited or foreign file is replaced by the current time and counted (not rejected), so one bad field does not cost the note.
- YAML bombs and nesting. Mitigated by the 1,000,000-byte cap checked before reading, the no-alias loader, the 200-entry cap and the `RecursionError` mapping; measured in assumption (l); behaviour inside a worker thread is unverified until criterion 4 runs.
- 200 embedding calls. With vectors on, one import can cost 200 sequential embedding calls and take a long time; the command shows no progress line (a limit, say so in the README) and is cancellable. A failing embedder switches the index off and the SQL rows stay; `/memory reindex` rebuilds the vectors later.
- Partial import on cancel or on a storage error: there is no transaction around the import; saved notes stay; a re-run skips them. A cancelled import prints no counts.
- Admin identity is self-chosen. `user_id` is a name the user picks, with no authentication (the same limit as publish and forget, README Known limits); `--shared` in `export` and `import` is not access control. An admin export with `--shared` writes shared notes of other users to a local file; an admin import with `--shared` publishes whatever the file holds under the admin's name.
- Exported files contain private notes in clear text. Mode `0600` and no overwrite protect against other local users and accidents, not against a backup tool, a synced folder or a later `chmod`. The README says so.
- Secrets: a note with a secret-looking string is refused on save, but an old or foreign file may contain some; such an entry is skipped and counted as invalid, never echoed (the same `redact` check as `save`, `memory.py:226-232`). A secret in a note's keyword is refused by the same rule.
- Exported ids are informational only: they are not preserved and cannot be used to update an existing note (merging is Out of Scope); two exports and imports of the same file are safe because of the `has_text` guard.
- Format versioning: `version: 1`; any other version is refused. A later format change bumps the number and keeps reading 1.
- Duplicate guard is by exact text only; a note whose text changed slightly is imported as a new note. `has_text` also treats a shared note of another user as known, so an importer never gets a personal copy of a shared note.
- Export larger than the import limits: 200 entries or 1 MB. Notes are at most 1500 characters, so about 200 notes fit within 1 MB; a larger store exports fine but must be split by hand to import (the answer says so for more than 200 notes; for a file over 1 MB the import says so).
- The path is on the machine running the harness. In the GUI that is the local machine (127.0.0.1); a GUI served to another host would write on the server. Not a supported setup, same as `/memory add @FILE`.
- Blocking inline awaits: the TUI and GUI await `/memory` answers inline today; an import of many notes would freeze the UI and make Escape and Stop useless, hence the task slot of a turn (criteria 29 and 30).
- Real PostgreSQL: the INSERT with explicit timestamps is pinned by statement text only; a run against a server is NOT done in this feature. The human may ask for the docker recipe in `tests/test_live_memory_postgres.py` later.
