## Problem / Motivation

Today a note enters memory only through the reflection after a turn (`Orchestrator._reflect`, `src/llm_harness/orchestrator.py:549`, one action per turn, gated on a tool use or a goal change) or through the `memory_save` tool. The human has no way to say "remember this" with a block of text they already have (a README paragraph, a meeting summary, a list of preferences): `handle_memory_text` is pure and never calls a model (`src/llm_harness/memory_command.py:285-325`), and the `/memory` verbs list, search, show, delete, publish, unpublish, forget and reindex only read or remove notes (`memory_command.py:30-40`). Saving by hand note by note is slow, and pasting everything risks duplicates of what memory already holds.

Human decisions (2026-11-04, recorded as decided):

- New command `/memory add [--shared] TEXT`: the user pastes text; ONE model call analyses it against the related existing notes (the user's and shared) and proposes ONLY NEW facts as one or several short notes. The model does the de-duplication.
- Reply format: ONE flat JSON object with parallel arrays, `{"notes": [...], "keywords": [...]}`, where `keywords[i]` is a comma-separated string for note `i`. One model call per add. At most 5 notes. A length mismatch between the arrays is rejected.
- Text over 4000 characters is REFUSED with `text too long (N characters, at most 4000); add it in parts`. No chunking, no silent cut.
- The harness shows a numbered preview; `/memory add confirm` saves the notes, `/memory add cancel` discards them. The pending preview lives for the session only.
- Personal by default; `--shared` only for users listed in `[tools] memory_admins`.
- `/memory import` and `/memory export` are a separate roadmap item (`memory-yaml-transfer`).
- HUMAN DECISION (2026-11-04, added when the spec was approved): "allow specifying text/markdown file". `/memory add` must also accept a text or markdown FILE, not only pasted text.

Assumptions (the human may change them):

- (a) Forms: `/memory add [--shared] TEXT...` (`--shared` only as the first word after `add`), `/memory add confirm`, `/memory add cancel`. Exactly the words `confirm` and `cancel` as the only word after `add` are reserved; `/memory add --shared confirm` and `--shared cancel` also give usage (decision: they must not silently become a shared add of the text "confirm"). Empty TEXT (`/memory add`, `/memory add --shared`) gives usage. TEXT is the rest of the line after `add [--shared]`, taken with `text.split(None, 2)` style slicing, not re-joined from `text.split()`, because `parse_memory_command` collapses whitespace today (`memory_command.py:67`) and the 4000 limit and the model should see the text as typed (trimmed). `MemoryCommand` gets a `shared: bool = False` field; actions `add`, `add-confirm`, `add-cancel`.
- (b) The model call is a new method `Orchestrator.propose_memories(paste, shared)`. It reuses `_memory_target` (`orchestrator.py:533`), a 60 s timeout (a new constant, or `REFLECTION_TIMEOUT_SECONDS`, `orchestrator.py:96`; decide at implementation, the same value), the usage report and a recorder span named `memory_add`. It uses the orchestrator's own chat model through `self._provider.stream_chat`, with no tools in the `ChatRequest` and one attempt, like the reflection (`_collect_reflection`/`_read_reflection`, `orchestrator.py:619-659`). It returns a small result (the proposed notes and the `UsageReport` or None) instead of yielding events. `handle_memory_text` gets two new optional keywords: `propose` (a callable bound to that method) and `pending` (a small mutable holder owned by the front end; the function itself stays stateless). `memory_command.py` contains no model code. The call is made in `handle_memory_text`, only after parse, memory gate and admin check pass. When a front end has no Orchestrator (`_orchestrator is None` in the TUI and GUI after a failed model pick, `tui/app.py:316`, `gui/app.py:400-405`), the answer is `no working model: pick another and press Ctrl+N` (TUI) or `press New chat` (GUI), the same words those front ends already use; `confirm` and `cancel` need no model and still work.
- (c) The prompt lives in a new `src/llm_harness/prompts/memory_add.md`. The paste is untrusted: it goes into a `<pasted-text>` data block through `scrub_block_text` like `_turn_record` (`memory_reflection.py:252-263`) with a fixed sentence saying it is data, never instructions. Related notes are `store.search(user_id, paste, RECALL_K)` rendered with `format_recall_block` (`memory_recall.py:36`); the search keeps only the first 32 meaningful words of the paste (`_MAX_QUERY_TERMS`, `memory.py:148`, applied in `_query_words`, `memory.py:281-290`), so a long paste is matched on its beginning only. The model returns only NEW facts and `{"notes": [], "keywords": []}` when nothing is new; the answer is then `nothing new to add` and nothing is pending.
- (d) A new pure module `src/llm_harness/memory_add.py`: `ProposedNote`, `parse_proposals(text)`, `add_schema()`, `build_add_request(model_cfg, paste, memories, think)` (through `build_side_request`, `context.py:167`) and `PendingProposals` (user id, shared flag, notes). Fenced and unfenced JSON are handled like `parse_reflection` (`_unfence`, `state.py:258`, used by `parse_reflection`). A reply that breaks the contract answers `memory add failed: <reason>` and leaves nothing pending. Validation of each proposed note uses the store's own checks BEFORE the preview, through one new public helper in `memory.py`, `validate_note(text, keywords) -> tuple[str, tuple[str, ...]]`, that wraps the private `_check_text` and `_check_keywords` (`memory.py:235`, `:253`): single line, 1 to 1500 characters, 1 to 8 distinct keywords of the allowed shape, secret-free. Decision: an invalid note is DROPPED, the valid ones are kept, and the preview ends with one line `dropped K invalid notes: #2 not one line, #4 looks like a secret`. The reason is a FIXED phrase per failure class (`empty or over 1500 characters`, `not one line`, `bad keywords`, `looks like a secret`), never the store's message, because the keyword message echoes up to 30 characters of the keyword (`memory.py:266-270`). If every note is invalid the answer is `memory add failed: no valid note in the reply` with the same reasons. Reason for dropping rather than rejecting the whole proposal: one bad note from a 12B model should not cost the other four, and the human reads the preview anyway. Keywords: `keywords[i]` is split on commas, each part trimmed; empty parts are ignored; no lower-casing (a capital letter is a bad keyword and the note is dropped).
- (e) Preview text: numbered lines `N. [kw1, kw2] text` (with a `[shared]` marker after the number when `--shared`), then the final line `/memory add confirm to save N notes, /memory add cancel to discard`, then the usage line of the model call (`format_usage_report`, `display.py:47`) like the reflection shows. The text is escaped like the other answers (`_escape`, `memory_command.py:95`). The answer to an add says the preview is kept for this session only. A new `/memory add TEXT` replaces an existing pending preview and says `replaced the pending preview of N notes`.
- (f) `confirm` needs a pending preview, else `nothing to confirm`. It re-checks that the pending `user_id` equals the current one and, for a shared preview, that the user is in `memory_admins` (the check lives only in the command, like `_publish`, `memory_command.py:180-203`). It saves note by note with `store.save(user_id, text, keywords, shared=...)` (there is no batch method). It skips a note whose exact text already exists for the user or as a shared note: decision, a new small store method `MemoryStore.has_text(user_id, text) -> bool` (`SELECT 1 FROM memories WHERE text = ? AND (user_id = ? OR shared = 1)`), deterministic, rather than `search`, which ranks by words, keeps 32 words and cannot prove absence. Answer: `saved N of M memories (#id, #id); skipped K already known`. A note whose save raises `MemoryValidationError` is reported with its message and the others continue; a `MemoryStorageError` message (type name only) is reported the same way. The pending preview is cleared afterwards, whatever the result. `cancel` clears it: `discarded N proposed memories` or `nothing to cancel`.
- (g) `MemoryStore.save(user_id, text, keywords, shared: bool = False)`: today `save` inserts no `shared` column (`memory.py:344-355`), so the INSERT gains `shared` on both dialects. `IndexedMemoryStore.save` (`memory_index.py:169-172`) passes it; `_payload` already writes `shared: 1` for a shared note (`memory_index.py:100-101`). The admin check lives only in the command; no tool path gets a `shared` argument: `MemorySaveInput` and the `memory_save` tool schema stay as they are, and `memory_tools.py` and `memory_reflection.py` do not mention the add path.
- (h) Memory must be on (`_memory_target`), else the existing `MEMORY_OFF` answer (`memory_command.py:28`). Vectors are not required: related notes come from the keyword search (`IndexedMemoryStore.search` fuses vectors when they are on).
- (i) Pending state: one `PendingProposals` holder per front end, next to `_orchestrator` (`cli.py:595` local variable of the chat setup, `tui/app.py:194`, `gui/app.py:237`). It is cleared in `_start_session` (new chat and model change) and on quit; it is never written to disk.
- (j) Cancellation: the add call must run in the same task slot as a turn so that Escape (TUI) and Stop (GUI) cancel it. TUI: `run_worker(..., group="turn")` like the turn (`tui/app.py:321-323`; `action_cancel_turn`, `tui/app.py:406-408`). GUI: the `self._turn` task (`gui/app.py:410`, `_on_stop` at `:418`) with `_set_busy(True/False)`. Plain mode: Ctrl-C already ends the process (`cli.py:624`). A cancelled call leaves nothing pending. A short `[memory: proposing...]` line is shown before the call; no spinner exists in any front end.
- (k) Rendering: GUI `self._show(text, "memory", "w-full")` (`gui/app.py:395`, full width, same text size as other answers, no new layout code); TUI `self._show(text, "note")` (`tui/app.py:309`); plain stdout.
- (l) `USAGE` and the `/memory` COMMANDS entry gain `add [--shared]`; `/help memory` still equals `USAGE` (`commands.py:48-54`, the detail is `MEMORY_USAGE`); the drift tests stay green.
- (m) Docs: README (the command table, the Agent memory section: how add works, preview and confirm, the limits, the single-line inputs), CHANGELOG `Added`, `specs/memory.md` entries only if durable. The constitution edits are described in Approach (Constitution impact).

File form, design assumptions added with the human decision above (the human may change them):

- (n) Form: `/memory add [--shared] @PATH`. The rest of the line after `@` is the path, stripped, and may contain spaces; `~` is expanded like `resolve_path` (`src/llm_harness/state_files.py:57-61`, `Path(argument).expanduser()`), which the loader reuses (an empty path after `@` gives usage, so `resolve_path`'s empty-argument default is never reached). `MemoryCommand` gets a `from_file: bool = False` field next to `shared`; the action stays `add`. `@` as the first character of TEXT means a file; a text that merely starts with `@` is not a use case, and a user who wants to add text starting with `@` rephrases it (for example puts a word before the `@`). An `@` anywhere else in the text is plain text. `check_size` (`src/llm_harness/state_io.py:70`) and `read_import` (`state_files.py:98-117`) do not fit as they are, because both are fixed to the 1,000,000-byte cap (`MAX_IMPORT_BYTES`) and to `StateImportError`; the loader follows the same order as `read_import` (stat, regular-file check, size check, then read at most one byte past the cap) and does not duplicate `resolve_path`. Whether to give `read_import` a cap argument instead is decided at implementation.
- (o) Checks, in this order, each a one-line refusal: extension `.txt`, `.md` or `.markdown`, case-insensitive, else `only .txt, .md and .markdown files can be added`; the path must exist, else `no such file: <escaped path>`; it must be a regular file (symlinks are followed), else `not a regular file: <escaped path>`; the byte size from `stat` BEFORE reading, above 64 KB (65536 bytes) refused with `file too large (N bytes, at most 65536)`; the bytes read as strict UTF-8, else `file is not valid UTF-8 text`; an empty file (after the BOM strip and trim) gives `file is empty`; then the SAME 4000-character limit as pasted text applies to the decoded text, `text too long (N characters, at most 4000); add it in parts`. The human chose refusing over 4000 for pasted text; the same limit for files is the default and is changeable (chunking of long files is a later feature, Out of Scope).
- (p) Newlines in a file are fine: the file text goes to the model inside the untrusted data block, and the notes are still saved one line each, produced by the model. `\r\n` is normalised to `\n` and a UTF-8 BOM is stripped before the length check and before the text is sent.
- (q) An error never echoes a raw control character: every path in an answer goes through the same `_escape` as the other `/memory` answers (`memory_command.py:95`, public alias `escape_text`). `memory_command.py` will import the loader, so the loader cannot import `_escape` from it without an import cycle; at implementation either the function body moves to a lower module (`llm_harness/display.py`, next to `sanitize_text`) with `_escape` and `escape_text` kept as names in `memory_command.py`, or the loader error carries the unescaped path and the command escapes it. Either way no answer shows a raw control character.
- (r) Order inside `handle_memory_text` for `--shared @PATH`: parse, memory gate, the `--shared` admin check FIRST, then the file read, then the model call. A non-admin never causes any filesystem access. The read is a small blocking read and runs off the event loop with `asyncio.to_thread`, the pattern already used in `src/llm_harness/web_extract.py:36`; it finishes before the model call starts.
- (s) Privacy: the file text goes to the MODEL PROVIDER like any chat text, so its content leaves the machine for the configured provider. A secret-looking string inside the file is sent to the provider even though a note containing it is refused on save (the validation of criterion 22 runs on the proposed notes, after the call). The human chooses the path deliberately; the harness never reads a file the human did not name on the command line. The model has no tool to name a path, and no tool path reaches the add path.
- (t) All three front ends: the harness runs locally and the path is on the machine that runs the harness. The GUI runs on 127.0.0.1; there the path is typed into the chat input, with no upload dialog (an upload button is Out of Scope).
- (u) Because the single-line inputs cut or split a multi-line paste (next paragraph), the file form is the documented way to add multi-line or markdown content; the README says so.

Pasted newlines, from code (not run in a front end): the TUI `Input` keeps only the FIRST line of a terminal paste (`textual/widgets/_input.py:756-759`, `event.text.splitlines()[0]`), so a multi-line paste is silently cut to its first line; the Ctrl+V binding calls `action_paste`, which replaces with the clipboard text unchanged (`_input.py:1129-1133`), whether newlines then survive is unverified. The plain mode reads one line at a time (`_read_line`, `cli.py:156`; `_chat_loop`, `cli.py:240-270`), so a multi-line paste arrives as several lines: line 1 is the `/memory add ...` command and every later line is handled on its own, as another command or as a normal user turn sent to the model. The GUI input is a NiceGUI `ui.input` (a Quasar `q-input` around a native `<input>`, `nicegui/elements/input.js`); a single-line `<input>` does not hold newlines in a browser, but what a browser does with a pasted newline (strip or replace) is unverified here. So the practical pasted input is ONE line; the file form `/memory add @PATH` is the way to add multi-line or markdown content.

## Acceptance Criteria

Two steps. Criteria 1 to 13 belong to step 1 (offline unit and orchestrator tests, and the file loader tests with `tmp_path`); criteria 14 to 30 belong to step 2. All run offline with `ScriptedProvider` (`tests/fakes.py:35`), `FakeVectorStore`, and a real `SqliteRelationalStore` on `tmp_path`. No live model and no live PostgreSQL run is required.

1. **Parse: the add forms.** `/memory add some text` gives `MemoryCommand("add", query="some text", shared=False)`; `/memory add --shared some text` gives `shared=True`; `/memory add confirm` and `/memory add cancel` give `add-confirm` and `add-cancel`; `/memory add`, `/memory add --shared`, `/memory add --shared confirm` and `/memory add confirm now` (the last is a plain add of the text `confirm now`) are checked against assumption (a); spacing inside TEXT is kept. The file forms: `/memory add @/tmp/a.md` gives `MemoryCommand("add", query="/tmp/a.md", shared=False, from_file=True)`; `/memory add --shared @~/my notes.md` gives `shared=True` and the path `~/my notes.md` (spaces kept, stripped); `/memory add @` and `/memory add --shared @` give usage; `/memory add see @x` is plain text with `from_file=False`.
2. **parse_proposals: valid and fenced replies.** A flat object with equal-length `notes` and `keywords` parses to `ProposedNote` values; one code fence around the whole reply is tolerated; keywords strings are split on commas and trimmed.
3. **parse_proposals: empty arrays.** `{"notes": [], "keywords": []}` parses to no notes (not an error).
4. **parse_proposals: contract breaks.** A length mismatch, more than 5 notes, a non-string note, a non-string keywords entry, `notes` or `keywords` not a list, a missing key, an extra key, a non-object reply and invalid JSON each raise the parse error with a message that names the problem.
5. **Schema is flat.** `add_schema()` has no `$ref`, no `$defs` and exactly one `"type": "object"`, like `tests/test_memory_reflection.py:297-301`.
6. **build_add_request: untrusted text and related notes.** The request has two messages (system, user) and no tools; the paste sits inside the data block with the data-not-instructions sentence; a paste that contains the closing tag or a `## ` heading cannot close the block or forge a heading; the related notes block from `format_recall_block` is present, `[shared]` marker included.
7. **propose_memories: gate off.** With memory off (no storage, no `user_id`, or no `memory_search` tool, `_memory_target` is None) it makes no model call and returns the off result.
8. **propose_memories: success and usage report.** With a scripted reply it returns the notes and the `UsageReport` of the call; the request used the orchestrator's model, carried `response_schema` and no tools.
9. **propose_memories: timeout and provider error.** A provider that hangs (`hang_after`) hits the timeout (the constant monkeypatched small) and an `ErrorEvent` reply gives a failure result with the reason, like the reflection (`no answer within 60 seconds`, `provider error (...)`); no retry (one request recorded); the span `memory_add` has status error.
10. **propose_memories: cancel.** Cancelling the awaiting task propagates `CancelledError` and the provider stream is closed.
11. **Store: `save(shared=True)` and `has_text`.** On SQLite and on the Postgres statement-text fake, `save(..., shared=True)` stores `shared = 1`, another user sees the note as shared in `list` and `search`, `IndexedMemoryStore.save` writes the vector payload `{"user_id": ..., "shared": 1}`; `save` without the argument still makes a private note; `has_text` is true for the user's own text and for a shared text of another user and false for another user's private text.
12. **Loader: success.** `read_text_file(path) -> str` (a function with no model or store access) returns the text of a `.txt`, a `.md` and a `.markdown` file, of an uppercase extension (`NOTE.MD`), of a path starting with `~` (the home directory pointed at `tmp_path` through the environment, as `resolve_path` expands it), of a path with spaces, of a file with `\r\n` line ends (returned with `\n`) and of a file with a UTF-8 BOM (returned without it); a symlink to a regular `.md` file is followed. All with files under `tmp_path`.
13. **Loader: each refusal.** The typed error (a `ValueError` subclass, one safe line, no newline) with the exact message for: a wrong extension (`only .txt, .md and .markdown files can be added`), a missing file (`no such file: <escaped path>`), a directory named `x.md` (`not a regular file: <escaped path>`), invalid UTF-8 bytes (`file is not valid UTF-8 text`), an empty file and a BOM-only or whitespace-only file (`file is empty`), a file of 65537 bytes (`file too large (65537 bytes, at most 65536)`, refused from `stat` without reading; a file of exactly 65536 bytes of ASCII is not refused for size) and a decoded text of 4001 characters (`text too long (4001 characters, at most 4000); add it in parts`; exactly 4000 is accepted). A path with a newline, an ESC and a bidi character in its name (created under `tmp_path` where the platform allows it, else passed as a missing path) appears in the message only escaped (`\uXXXX`), never raw.
14. **Command: add shows a numbered preview.** `handle_memory_text("/memory add TEXT", ..., propose=...)` with a scripted two-note reply answers numbered lines `N. [kw, kw] text`, the confirm/cancel line, the session-only sentence and the usage line; nothing is stored yet.
15. **Command: confirm saves personal notes.** After an add, `/memory add confirm` saves each note as a private note of the user (`shared` false), answers `saved N of M memories (#id, ...); skipped 0 already known`, and clears the pending state (a second `confirm` answers `nothing to confirm`).
16. **Command: `--shared` needs an admin, before any model call.** For a non-admin and for an empty `memory_admins`, `/memory add --shared TEXT` answers `NOT_ADMIN`-style refusal (a new constant, wording decided at implementation) and the scripted provider has recorded no request.
17. **Command: an admin adds shared notes.** For an admin the preview shows `[shared]`, `confirm` stores the notes with `shared = 1`, and another user sees them as `[shared]` in `/memory list`; `confirm` by a user who is no longer in `memory_admins` (a changed list) is refused and saves nothing.
18. **Command: cancel and confirm without pending.** `cancel` answers `discarded N proposed memories` and stores nothing; `cancel` and `confirm` with nothing pending answer `nothing to cancel` and `nothing to confirm`; neither calls the model.
19. **Command: a new add replaces the pending preview.** The second add answers that it replaced the first preview; `confirm` then saves only the second set.
20. **Command: over 4000 characters is refused.** A paste of 4001 characters answers `text too long (4001 characters, at most 4000); add it in parts` with no model call and nothing pending; exactly 4000 characters is accepted.
21. **Command: nothing new and failures.** A reply with empty arrays answers `nothing new to add` and nothing is pending; invalid JSON, a timeout and a provider error answer `memory add failed: <reason>` and nothing is pending; memory off answers `MEMORY_OFF` with no model call.
22. **Command: an invalid proposed note is dropped without an echo.** A reply with a secret-looking note (an API-key-shaped string), a two-line note, an over-long note and a bad keyword: the preview lists only the valid notes and the dropped line names the numbers and the fixed reasons; the secret text and the bad keyword text appear nowhere in the answer; after `confirm` nothing of them is in the store; all invalid gives `memory add failed: no valid note in the reply`.
23. **Command: exact duplicates are skipped and partial failure is reported.** A proposed note equal to an existing own or shared note is skipped (`skipped K already known`); a note that fails at save time (the store is made to raise `MemoryValidationError` for one note) is reported with its message and the other notes are still saved.
24. **Command: file form, preview and confirm.** `/memory add @<tmp file>` with a scripted two-note reply reads the file, answers the same numbered preview as criterion 14, and `/memory add confirm` then saves the notes (private); the request the scripted provider recorded contains the file text (CRLF normalised, BOM stripped) inside the data block and does NOT contain the path; a file whose decoded text is 4001 characters is refused with the `text too long` message and no model call; a second add replaces the pending preview as in criterion 19.
25. **Command: `--shared @FILE` checks the admin before touching the file.** For a non-admin and for an empty `memory_admins`, `/memory add --shared @/nonexistent/x.md` answers the admin refusal of criterion 16, and a loader spy or raising stub patched into the command module is never called (no filesystem access), and the scripted provider recorded no request. For an admin the same form reads the file and the preview shows `[shared]`.
26. **Command: file refusals and threading.** Each loader refusal of criterion 13 reaches the user through the command as that one line, with no model call and nothing pending (the pending preview of an earlier add is handled as for the other failures of criterion 21); an `@` form with memory off answers `MEMORY_OFF` before any file access; the loader runs in a worker thread (a spy records `threading.get_ident()` different from the event loop thread) and finishes before the provider is called.
27. **Front ends: the GUI is primary and mandatory.** A NiceGUI `User` test (like `test_memory_publish_in_the_gui_needs_an_admin`, `tests/test_gui.py:1649`) types `/memory add ...` through `ask_memory` (`tests/test_gui.py:1633`, waiting on the `memory` answer element) and sees the preview, then `/memory add confirm` and sees the `saved` answer; no `user` turn element is created. A Stop test uses a `ScriptedProvider` with `hang_after`, presses Stop while `[memory: proposing...]` is shown, and checks that the controls are enabled again, the provider stream is closed and a following `/memory add confirm` answers `nothing to confirm`. A new chat after an add clears the pending preview. The GUI file test (primary, mandatory): the test writes a `.md` file under `tmp_path`, types `/memory add @<tmp file>` into the chat input (no upload element), sees the preview, then types `/memory add confirm` and sees the `saved` answer; the file text, not the path, reached the scripted provider.
28. **Front ends: TUI and plain mode.** The TUI test (like `test_memory_publish_in_the_tui_needs_an_admin`, `tests/test_tui.py:1244`, answer read from the `note` element) covers add (text and `@<tmp file>`), confirm, cancel and an Escape that cancels a hanging add with nothing pending; the plain-mode test (like `test_plain_publish_needs_memory_admins_in_the_config`, `tests/test_memory_command.py:868`) covers add (text and `@<tmp file>`), confirm and cancel through `main` with a scripted provider and shows what a second pasted line does.
29. **Tool safety pin.** A test asserts that the new add path (names such as `propose_memories`, `PendingProposals`, `memory_add`) does not occur in the source of `llm_harness.memory_tools` and `llm_harness.memory_reflection`, that the `memory_save` tool input schema still has no `shared` property (the existing pin around `tests/test_memory_tools.py:560`), and that `shared=True` is passed to `save` only from `memory_command.py`.
30. **USAGE, COMMANDS, help, docs.** `USAGE` names `add [--shared]` on its first line (`/memory add [--shared] TEXT`) and has an `  add` description line that names the `@FILE` form; the COMMANDS entry gains `add` in its arguments string and description; `help_detail` for each front end still equals `USAGE` (`test_memory_detail_is_exactly_the_memory_usage`, `test_memory_detail_is_not_a_copy` in `tests/test_commands.py`); the pins that break by design are updated (see Affected Areas); README documents the command, the `@FILE` form (accepted extensions, the 64 KB and 4000-character limits, the privacy note of assumption (s), and that the file form is the way to add multi-line or markdown content) and CHANGELOG has an `Added` line that mentions the file form; `uv run pytest` (default suite), `ruff check` and `ruff format --check` are green.

## Approach

Memory consulted: grep of specs/memory.md for `gemma|flat|reflect|handle_memory_text|shared|payload` — 6 relevant entries (lines 18, 19, 82, 84, 85, 86; no entry is about the reflection contract itself): gemma4:12b through Ollama wraps JSON in a fence and sends fields as the wrong type unless the schema is explicit and flat (hence the flat parallel-array reply, a fence tolerated by the parser); `handle_memory_text` appends `store.take_notice()` to every `/memory` answer, so `add`, `confirm` and `cancel` get it too; the vector payload is `{"user_id": ...}` plus `"shared": 1`, and `_fused` drops a vector-only hit unless `get` returns the note (a shared save must therefore reach both the row and the payload).

An ordered plan of exactly two implementation steps, each ending with green tests.

STEP 1: the pure parts and the model call.

File form (human decision 2026-11-04, "allow specifying text/markdown file"): `/memory add [--shared] @PATH` reads one `.txt`, `.md` or `.markdown` file of at most 64 KB through `read_text_file` (STEP 1) and from there on behaves exactly like pasted text: the same 4000-character limit on the decoded text, the same single model call, preview, `confirm` and `cancel`. The admin check for `--shared` runs first, the file is read next in a worker thread, the model call comes last. The file text is sent to the configured model provider like any chat text: its content leaves the machine, a secret-looking string in the file is sent although a note containing one is refused on save, and the human chose the path deliberately. All three front ends take the same form; in the GUI the path is typed into the chat input.

Risks, inside the approach:

- gemma4:12b following the parallel-array contract is UNVERIFIED. Invalid JSON was seen before (memory.md line 18); the schema is flat and one fence is tolerated, but there is no live run. A model that returns arrays of different length gets the whole reply rejected (by decision). How a human can try it by hand: start the harness with a real `config.toml` that has `[tools] memory = true` and `user_id`, type `/memory add` with one line of facts, read the preview, then `/memory add cancel`.
- Prompt injection from the paste. The paste can tell the model to propose a note with attacker text. Mitigations: the preview and the explicit `confirm` are the human gate; the data block and the data sentence; every note is validated (single line, length, keywords, secret-free) before the preview; no tool path can reach the add path or the `shared` argument, and a `/memory` line reaches `handle_memory_text` only from human input before the orchestrator.
- Partial saves: `save` has no batch method, so `confirm` may save some notes and fail on others; the report lists the ids saved and the failures.
- Single-line inputs: the TUI cuts a terminal paste to its first line; the plain mode turns every later pasted line into its own input (possibly a model turn); the GUI behaviour is unverified (see Problem / Motivation). The README says to paste one line and to use the file form for multi-line or markdown content.
- Privacy of the file form: the whole decoded file text (up to 4000 characters) is sent to the configured model provider; secret-looking strings in it are sent too, because the secret check runs on the proposed notes after the call. The human names the path; nothing reads a file on its own. The README states this.
- File form edge cases: a path is stat-ed and then opened, so a file replaced between the two steps is possible; the read is capped at one byte past 64 KB and the size is checked again, so the cap holds. A named pipe or device is refused as not a regular file. A text that starts with `@` is always read as a file path (assumption (n)).
- The pending preview is lost on new chat, model change and quit, by design.
- Cost: one model call per add on the orchestrator's chat model; the usage line is shown after the preview.
- De-duplication relies on the model plus the exact-text guard; a near-duplicate with different words can still be saved after a human `confirm`.
- Blocking inline awaits: TUI and GUI handlers await `/memory` today (`tui/app.py:301`, `gui/app.py:387`), which would freeze the UI for up to 60 s and make Escape and Stop useless; hence the task slot of a turn (criterion 27 and 28).
- Related notes are found from the first 32 meaningful words of the paste only (`_MAX_QUERY_TERMS`), so a note related to the end of a long paste may be missing from the model's context.
- `Orchestrator.propose_memories` needs the chat model to be able to answer a side request while a turn is not running; the front ends refuse an add while a turn is running (`_turn_is_running`), the same as a normal message.

Constitution impact (the human approved the earlier wording on 2026-11-04 and asked for the file form; applied in the same change as this version): `specs/mission.md` (version 24 to 25), in the `/memory` clause, the phrase ", and `/memory add TEXT` (or `/memory add @FILE` for a `.txt` or `.md` file) makes one model call that proposes only the new facts of the text as short notes, shown as a numbered preview that `/memory add confirm` saves and `/memory add cancel` discards (`--shared` for a user listed in `[tools] memory_admins`)" inserted directly after "embeds every note again)". `specs/tech-stack.md` (version 35 to 36), after the memory sentences, one sentence: "`/memory add` is the only `/memory` action that calls a model; it uses the orchestrator's chat model, one call, no tools, and its text comes from the command line or from a `.txt`, `.md` or `.markdown` file." `specs/roadmap.md`: the item `memory-add-command` moved from Next to Now (the normal `/code` bookkeeping); delivery removes the Now line.

## Out of Scope

- Chunking of long text (over 4000 characters is refused), pasted or from a file; the same limit for files is the default and may change, and a later chunking feature would cover long files.
- Update or forget proposals (add only).
- Editing a preview before confirm.
- Several pending previews at once.
- Persistence of a pending preview across restarts, new chats or model changes.
- YAML import and export (`memory-yaml-transfer`).
- A spinner (a one-line notice only).
- A live-model probe and a live PostgreSQL run (not done; the model contract stays unverified against a real model).
- Multi-line input widgets, an upload button or dialog in the GUI, a file picker in the TUI.
- Other file types (PDF, docx, HTML), directories, several files in one add, URLs, and any tool that lets the model name a path.

Behaviour choices of the engineer (changeable assumptions, not in the approved criteria):

- A failed add (refusal, error or `nothing new to add`) discards an earlier pending preview and appends `discarded the pending preview of N notes` (`memory_command.py:387`); a successful add prefixes `replaced the pending preview of N notes` (`memory_command.py:386`). The human may prefer a failed add to keep the old preview.
- Counts are not pluralised: `1 notes`, `saved 1 of 1 memories`.
- Preview order: the notes, the `dropped K invalid notes: ...` line, the confirm/cancel line, the session-only sentence, then the usage line (`memory_command.py:431-439`).
- `_invalid_reason` returns one of four fixed phrases and never echoes store text; a save-time validation message is escaped and clipped to 80 characters (`memory_command.py:482`).
- Memory off answers `MEMORY_OFF` for add, confirm and cancel; the TUI and GUI pass their own no-model wording (`no working model: pick another and press Ctrl+N` and `... press New chat`).
- Pasted multi-line input (engineer-observed): the TUI keeps only the first line (test `test_a_pasted_multi_line_text_keeps_only_its_first_line_in_the_tui`); plain mode treats the second pasted line as its own input, which goes to the model as a normal turn while the preview survives.
